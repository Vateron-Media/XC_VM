    Основное расширение (xcvm_core): Что оно делает, хранит, отправляет — и чего не делает¶

    Эта страница предназначена для XC_VM пользователей и администраторов. Основная часть (xcvm_core.so) поставляется в виде скомпилированного двоичного файла без исходного кода, и это является законной причиной для задавать вопросы. Итак, на этой странице описано все его поведение: что происходит при время загрузки, какие файлы он создает, каждое действие, которое он может выполнить, каждая сеть запрос и что именно содержит каждый из них, как работает лицензирование и что именно происходит, когда лицензия отзывается, а также что делает ядро нет и как это сделать проверяйте каждое утверждение самостоятельно со стандартными инструментами Linux, без исходных текстов.

    Страница является самодостаточной: она не отсылает вас больше никуда.

    1. Вкратце: что это такое¶

    xcvm_core - это собственное расширение PHP (написанное на Rust), которое загружается в PHP процессы панели XC_VM и регистры класса один, XC_VM со статическим методы. Он не добавляет никаких глобальных функций и не устанавливает никаких перехватчиков в код PHP исполнение.

    Это решает ровно три проблемы:

    Проблема Что он делает
    Config, DB, Redis Сохраняет настройки панели в зашифрованном виде, используя машинные config.enc и ручные PHP готовые MySQL/Redis соединения, чтобы пароли никогда не появлялись в коде PHP.
    Modules Загружает модули из хранилища, удаляет транспортное шифрование и сохраняет файлы, закодированные в ionCube, на диске, которые выполняет стандартный загрузчик ionCube
    Licence and cluster Проверяет лицензию на установку и позволяет главному серверу передавать конфигурации и токены узлов LB без передачи паролей

    Это нет: черный ход, канал дистанционного управления, средство сбора телеметрии, способ для эксфильтрации ваших данных или механизма выполнения кода, отправленного извне. То ниже приводится подробная информация по каждому из этих утверждений.

    2. Почему ядро является двоичным¶

    Код панели PHP открыт и может быть прочитан любым пользователем, имеющим доступ к серверу. Если пароли баз данных, ключи шифрования или ключи платных модулей хранятся в нем, они будут отправляться первому, кто открыл файл. Таким образом, именно эти данные будут перенесены в скомпилированный код:

    1. Пароли к базе данных и Redis никогда не появляются в PHP: ядро считывает их из config.enc сам по себе и сам открывает соединение.
    2. Ключи модуля никогда не появляются в PHP: ядро извлекает их с сервера сам по себе, расшифровывает файлы во время установки и сохраняет ключ в зашифрованном виде.
    3. Проверка лицензий нельзя закомментировать, отредактировав PHP.

    В этом весь смысл закрытого двоичного файла. Его поведение не является секретом — это описано здесь.

    3. Что происходит при загрузке PHP¶

    В начале каждого процесса PHP (php-fpm, CLI) ядро инициализируется. Это полный список того, что произойдет потом — и ничего больше:

    1. Проверка с помощью отладчика. Файл /proc/self/status прочитан. Если процесс завершен отслеживается прямо сейчас (TracerPid ненулевое значение - например, подключен gdb), ядро отказывается загружаться. Больше ничего не происходит: ничего не удаляется, ничего отправляется куда угодно, сервер не останавливается — класс XC_VM просто недоступен в этом процессе.
    2. Регистрация директивы ini xcvm_core.server_url (см. раздел 8.4).
    3. Проверка наличия загрузчика ionCube. Если он не загружен, выдается обычное PHP предупреждение передается. Это всего лишь сообщение — ядро продолжает работать.
    4. Идентификатор установки. Если файл install_id еще не существует, генерируется случайный UUID и записывается в каталог конфигурации с 0600 разрешения. Если он существует, то будет прочитан.
    5. Автоматическая миграция конфигурации. Если в конфигурации есть старый открытый текст config.ini каталог, а config.enc - нет, ini считывается, шифруется в config.enc, и config.ini тогда равно удаленный (таким образом, пароли в виде открытого текста не сохраняются диск). Если config.enc уже существует, ничего не происходит. Если не существует ни того, ни другого, ничего не происходит.

    Ядро не выполняет никаких сетевых запросов во время загрузки. Каждый запрос к сервер работает только внутри вызовов методов, перечисленных в разделе 5.

    Ядро не создает фоновых потоков, таймеров, демонов или заданий cron. Все, что в нем есть это происходит внутри вызова метода, созданного панелью, и заканчивается этим вызовом.

    4. Что ядро хранит на вашем диске¶

    Все секретные данные для каждой установки хранятся в каталог конфигурации — по умолчанию /home/xc_vm/config (разрешения 0700). Путь может быть переопределен с помощью XCVM_CONFIG_DIR переменная окружения — переменная окружения только, которая ядро считывает данные.

    Файл Что это такое Режим
    config.enc Настройки панели (база данных, Redis, роль сервера), шифрование AES-256-GCM. Ключ получен из install_id и /etc/machine-id, таким образом, копия на другом компьютере не расшифровывается 0600
    install_id Случайный UUID вашей установки. Создается один раз и никогда не изменяется (несмотря на обновления ядра и PHP) 0600
    panel.pk / panel.sk The panel's X25519 key pair. The public half is sent to the server at registration; the private half never leaves the machine and is stored sealed to this machine's key ск: 0600
    module_keys/<module>.key Транспортный ключ шифрования каждого установленного платного модуля, который сам по себе зашифрован с помощью главного ключа установки 0600
    activation_key Лицензионный ключ активации (вы вставляете его в панель). Подписан сервером, привязан к вашему install_id 0600
    license_verdict Кэш последнего подписанного ответа сервера о состоянии лицензии 0600
    license_checkin Временная метка, указывающая, когда может состояться следующая ежедневная регистрация заезда (см. раздел 7). —
    license_enforce_ts / license_revoked Временные метки последнего применения отозванной лицензии и сама отметка об отзыве (см. раздел 7.4) —
    cluster/ Файлы кластера: корневые ключи MAIN (root.enc), закрепленные ключи MAIN на LB (core.pin), состояние отзыва узла (nodes.state), защищенные часы (clock.sealed, timeanchor), аренда LB (lease). Все зашифровано с помощью ключа этой машины 0600

    За пределами каталога конфигурации ядро записывает:

    • to /home/xc_vm/Modules/<module>/ — файлы установленных модулей (путь указан следующим образом исправлено);
    • временный файл в /tmp с разрешениями 0600 — параметры подключения для mysqldump/mysql во время дампа/восстановления базы данных; файл ** удаляется сразу после операция**.

    Что записывает ядро нет: что-либо за пределами этих путей, скрытые файлы или изменяется на php.ini, cron, systemd или автозапуск.

    5. Полный список действий ядра¶

    Ниже приведены все методов класса XC_VM. Для каждого из них: что он делает, что он касается диска, базы данных и сети. Знак "—" в столбце "Сеть" означает, что метод не выполняет сетевых запросов. Ни один метод не запускается сам по себе — только когда панель называет это.

    5.1. Идентификация установки¶

    Метод Что он делает Диск Сеть
    install_id() Возвращает установочный UUID (создает его при первом вызове) считывает/создает install_id —
    env_fingerprint() Возвращает хэш SHA-256(install_id + /etc/machine-id + hostname). Это хэш: имя хоста или идентификатор компьютера не могут быть восстановлены из него считывает /etc/machine-id, имя хоста —

    5.2. Настройка панели управления¶

    Метод Что он делает Диск Сеть
    config_init(data) Записывает config.enc во время установки панели (база данных, Redis, роль сервера). Затем удаляет старый открытый текст config.ini записывает config.enc —
    config_set_redis(host, port, auth) Обновляет только раздел Redis раздела config.enc (требуется при изменении пароля Redis) записывает config.enc —
    config_server() Возвращает раздел server (идентификатор сервера, независимо от того, является ли он LB). Возвращает ли нет пароли считывает config.enc —
    config_set_db(pass) На узле LB: заменяет пароль базы данных на его config.enc (половина смены пароля узла). записывает config.enc —

    Каждая запись config.enc является атомарной: записывается временный файл, который затем переименовывается поверх старого. В случае сбоя в любой момент остается либо старый файл, либо новый, никогда не бывает пустым или испорченным.

    5.3. База данных и Redis¶

    Все методы считывают учетные данные из config.enc внутри ядра; ** они никогда не достичь PHP**.

    Метод Что он делает Диск Сеть
    db_connect() Возвращает готовое PDO-соединение с вашей базой данных считывает config.enc только ваша база данных
    redis_connect() Возвращает готовое соединение Redis считывает config.enc только для вашего Redis
    db_dump(file, ignore_tables) Выгружает базу данных через mysqldump (структура, затем данные) в данный файл записывает данный файл; временный .cnf в /tmp, после чего удаляется только ваша база данных
    db_restore(file, dbname) Отбрасывает и воссоздает заново в целевую базу данных, затем импортирует файл. Операция уничтожения, но она выполняется только по явному вызову с панели (восстановление из резервной копии) временный .cnf в /tmp, впоследствии удаленный только ваша база данных
    db_grant(host) Предоставляет привилегии пользователя панели управления базой данных при подключении с указанного адреса (для узла LB). — только ваша база данных
    db_revoke(host) Отменяет привилегии для данного адреса. Отказывается для отмены адресов MAIN сам может подключаться через (localhost, loopback, хост базы данных из конфигурации) — таким образом, MAIN никогда не будет отключен от своей собственной базы данных — только ваша база данных
    db_set_password(new) На ГЛАВНОЙ: изменяет пароль пользователя панели в базе данных, затем в config.enc, затем в разрешениях узлов. Если запись конфигурации завершается неудачно, пароль базы данных отменяется записывает config.enc только ваша база данных

    Адрес в db_grant/db_revoke строго проверен (допустимы только символы в хосте MySQL), и значения заключаются в кавычки с помощью PDO — SQL-инъекции через эти методы невозможны.

    5.4. Модули: хранение, установка, лицензия на модуль¶

    Метод Что он делает Диск Сеть
    panel_register(api_key) Регистрирует панель на сервере: создает (или считывает) пару ключей панели и отправляет install_id, общественный, env_fp и hw_id создает panel.pk/panel.sk panel/register
    plugins_check(plugin, install_id, api_key) Запрашивает у сервера, доступен ли модуль для установки — plugins/check
    plugins_token(plugin, install_id, api_key) Получает с сервера кратковременный (5-минутный) токен доступа к модулю — plugins/token
    extensions_list(env, api_key, options) Возвращает каталог магазина (постраничный, с поиском и сортировкой) — extensions
    extensions_check_update(list, api_key) Запрашивает, существуют ли обновления для списка установленных модулей — extensions/check-update
    module_install(slug, version, api_key) Полный цикл установки модуля (см. ниже) записывает Modules/<slug>/, module_keys/<slug>.key plugins/token, plugins/key, plugins/download
    module_license(slug, server_data, api_key) Запрашивает файл лицензии ionCube .lic для модуля, подключенного к вашему компьютеру — (панель записывает файл) plugins/token, plugins/license

    Как устанавливается модуль (module_install), шаг за шагом:

    1. С сервера запрашивается токен доступа к модулю. Сервер проверяет, является ли владелец ключа API имеет право на доступ к этому модулю. Для модуля свободный ни API-ключ, ни регистрация в панели управления не требуются.
    2. (Только для платных модулей.) Ключ транспортного шифрования модуля запрашивается у сервер. Он поставляется запечатанным с ключом вашей панели общественный, поэтому только ваша панель может откройте его с помощью его закрытого ключа.
    3. Ключ сохраняется в module_keys/<slug>.key — зашифрованном виде в соответствии с инструкцией по установке. главный ключ.
    4. Загружен архив модуля (tar.gz).     6. Сеть: каждый запрос и то, что он несет¶

    Ядро взаимодействует с только один внешний адрес — хранилищем и сервером лицензий https://www.xcvm.tech (каждый путь из /api/v1/). Он больше нигде не соединяется, кроме твой DB и твой Redis по адресам из вашей собственной конфигурации.

    6.1. Как строится каждый запрос¶

    Каждый запрос к серверу представляет собой POST, тело которого равно запечатанный для сервера. открытый ключ поверх TLS (конверт "XCVM-API-v1"). Внутри конверта находится временная метка, одноразовый идентификатор запроса, ключ API (при необходимости) и само тело запроса. Ответ сервера привязан к одноразовому ключу, известному только вашей панели, например это единственная просьба.

    Почему: чтобы тела запроса и ответа не могли быть прочитаны или заменены даже где TLS завершается на промежуточном этапе (прокси-сервер, load balancer, nginx→переход php-fpm на стороне сервера). Эта защита работает в вашу пользу: ваш API-ключ не передается в HTTP-заголовке и невидим на промежуточном сервере переходы, и загруженный модуль не может быть заменен при передаче.

    Параметры клиента:

    • Только HTTPS; включена проверка цепочки сертификатов и имени хоста, и ** не может быть отключено в любом месте** — в используемой библиотеке просто нет такой настройки;
    • в перенаправлении отказано (301/302 = ошибка);
    • тайм-ауты: обычный запрос - 15 секунд, загрузка архива - 120 секунд, подключение - 10 секунд;
    • размер архива не более 100 МБ;
    • ни на клиенте, ни на сервере нет режима открытого текста (незапечатанного).

    7. Лицензирование: как это работает и что происходит при отзыве лицензии¶

    Да, ядро проверяет лицензию. В этом разделе подробно описано, как и что происходит без доступа к сети и что происходит при отзыве. Ничего из этого не скрыто.

    7.1. Ключ активации¶

    Лицензия на установку представляет собой текстовый ключ формы XCVM1.<data>.<signature>, который администратор вставляет данные в панель; они сохраняются в файле activation_key. Ключ имеет значение подписанный сервером (Ed25519) и содержит:

    • hwid — ваш install_id: ключ работает только при той установке, при которой он был выдан для;
    • jti — идентификатор ключа;
    • iat — время выдачи;
    • exp — срок действия (может отсутствовать = бессрочный).

    Подпись, привязка и срок действия проверяются не в сети без подключения к сети.

    7.2. Требование об атрибуции¶

    Панель XC_VM распространяется под лицензией AGPL-3.0, и условия использования в лицензионных функциях сохраняется авторская принадлежность. Ядро проверяет это: оно считывает шесть собственных файлов панели (Core/Util/AdminHelpers.php и пять нижний колонтитул/шаблоны входа в систему на панелях администратора, реселлера и игрока) и следит за тем, чтобы строки атрибуции на месте (github.com/Vateron-Media/XC_VM, Vateron Media, ссылка на AGPL-3.0) и что вызов рендеринга нижнего колонтитула не является закомментировано.

    • The check is purely file-based: no network, no cryptography.
    • Если количество файлов равно отсутствовать (нестандартная компоновка, разработка), то проверка считается равным пройденный: ядро не блокирует установку из-за отсутствующих файлов.
    • Если атрибуция была удалена, license_valid() возвращает false, т.е. лицензированный функции (разветвление, чеканка кластерных токенов) отключены. Панель сами по себе ваши потоки, база данных и пользователи продолжают работать.
    • Вердикт кэшируется в течение 1 секунды, поэтому файлы не считываются при каждом запросе.

    7.3. Проверка и поведение сервера без подключения к сети¶

    На ГЛАВНОЙ странице license_valid() = "атрибуция установлена" и "ключ активации действителен". Срок действия включает в себя отзыв, и именно так ядро узнает об этом:

    • Ответ сервера о состоянии ключа кэшируется в license_verdict файл. Кэш подписан сервером и не может быть подделан.
    • Когда кэш устарел (или отсутствует), ядро внутри license_valid() вызывает — отправляет запрос activation/status; ответ проверяется подписью, с помощью однократно nonce и по jti, и только затем сохраняются в кэше.
    • На ОСНОВНОМ, дополнительно, один раз в день (20 часов плюс случайный сдвиг на 8 часов, чтобы избежать скачков нагрузки) вводится значение activation/checkin — те же данные. Узлы LB не проводите регистрацию заезда.

    Behaviour without server access — the key point:

    • Ключ, который сервер подтвердил хотя бы один раз , остается действительным в автономном режиме бессрочно. Недоступный сервер лицензийникогда не превращает оплаченный установка в неоплачиваемый режим.
    • Ключ, который сервер никогда не подтверждал (например, просто вставил, пока нет сеть) работает в течение 14 дней с момента его выпуска.
    • A licence is considered invalid in exactly two cases: the exp recorded in the сам ключ был передан, или сервер отправил ответ подписанный "ключ отозван". Сетевая ошибка, тайм-аут или неразборчивый ответ - это нет аннулирование.

    7.4. Что именно происходит при отзыве (приведении в исполнение)¶

    Об этом стоит знать заранее. Если лицензия недействительна подтвержденный (то два случая выше), и только на сервере главный ядро выполняет две функции:

    1. Записывает файл маркера license_revoked с временной меткой в конфигурацию каталог.
    2. Отменяет в вашей базе данных права доступа пользователя панели для LB/proxy адреса узлов (берется список адресов из вашей таблицы servers где is_main = 0 и выполняется REVOKE ALL PRIVILEGES для каждого). Каждый адрес сначала выполняется строгая проверка символов, чтобы исключить SQL-инъекцию через таблицу.

    Это выполняется максимум раз в час. Что он делает нет:

    • ❌ он не удаляет и не изменяет ваши данные — ни одной строки, ни одной таблицы;
    • ❌ это не затрагивает собственный доступ MAIN к своей базе данных;
    • ❌ это не останавливает PHP, nginx или потоки и не удаляет модули или файлы;
    • ❌ он ничего не отправляет на сервер;
    • ❌ Узлы LB никогда обеспечивают принудительное выполнение, что бы ни случилось.

    Цель: отозванная лицензия лишает установку возможности мультисерверный возможности (узлы теряют доступ к центральной базе данных), но не нарушает работу ни панели, ни данные. Доступ может быть повторно предоставлен с помощью обычного db_grant после истечения срока действия лицензии. восстановленный.

    7.5. Лицензия на узел LB¶

    Узел LB не содержит ключа активации. Для него license_valid() = "атрибуция в оформить" и "действительную аренду у MAIN" — разрешение, подписанное MAIN, с ограниченным сроком действия. срок службы, проверяемый по закрепленному ключу MAIN и оцениваемый по времени работы MAIN (время поворота обратный отсчет времени узла ничего не дает). Аренда позволяет узлу продолжать работать, пока основной временно недоступен.

    8. Защитные механизмы, которые обычно вызывают вопросы¶

    8.1. Защита от отладки¶

    Описано в пункте 1 раздела 3. Повторим ключевой момент: это всего лишь отказ от загрузка с помощью отладчика — без каких-либо побочных эффектов. Его назначение - блокировать ключи модуля извлекается из памяти запущенного процесса.

    8.2. Скрытые строки в двоичном коде¶

    Адрес сервера и два внутренних "перца" (константы, которые участвуют в ключевом вывод) хранятся в двоичном XOR-кодированном виде, поэтому strings xcvm_core.so не не показывать их. Цель состоит в том, чтобы предотвратить тривиальную переназначение ядра на поддельный сервер, и чтобы остановить вывод ключа, основываясь только на install_id. Это скрывает константы, а не поведение — поведение описано здесь полностью. Ключ-область такие имена, как xcvm_cfg_v1 и xcvm_module_v1, видны в strings, и это все в порядке.

    8.3. Машинная привязка: env_fp и hw_id¶

    • env_fp = SHA-256(install_id + /etc/machine-id + hostname). "Мягкий" переплет: сервер замечает клонирование или миграцию из-за изменения хэша, но измененный env_fp ничего не блокирует. Если идентификатор компьютера или имя хоста недоступны, это заменено пустой строкой.
    • hw_id = SHA-256(install_id + /etc/machine-id). Сервер сначала закрепляет его регистрация. Если то же самое install_id появится с другого компьютера, оплачиваемый модули перестают выдаваться с ошибкой panel_moved до тех пор, пока хранилище администратор сбрасывает привязку. Это защищает от копирования одного платного установка на множество серверов.

    Оба значения являются хэшами; по ним невозможно восстановить имя вашего хоста или идентификатор компьютера.

    8.4. Директива xcvm_core.server_url¶

    Другой адрес сервера может быть задан в виде php.ini, но только в виде зашифрованный — значение выдается инструментом владельца платформы. URL-адрес в виде открытого текста в этом директива игнорируется и используется встроенный адрес. Расшифрованный адрес должен быть https://. Цель состоит в том, чтобы остановить перенаправление ядра, изменив одно из них строка, отправленная в поддельный магазин, обслуживающий поддельные модули.

    8.5. Самоочищающиеся клавиши¶

    Ключи модулей, мастер-ключ, пароли баз данных и другие ключевые материалы хранятся в ядро в буферах, которые обнуляются в памяти при освобождении — на каждом пути выхода, включая ошибки.

    9. Чего нет в ядре¶

    • ❌ Черный ход или пульт дистанционного управления. Не существует метода, который выполнял бы команды или код, отправленный сервером. Сервер может ответить данными только на запрос, который составленная панель: каталог, жетон, ключ, архив, лицензионный вердикт.
    • ❌ Выполнение поставляемого кода ядром. Единственное, что приходит из сервер, а затем выполняется, является модулями, и они выполняются на складе Загрузчик ionCube с помощью обычного механизма PHP, после того как вы сами запустили установка. Ядро не устанавливает никаких перехватчиков для компиляции или выполнения PHP.
    • ❌ Телеметрия, шпионаж, утечка данных. Полное содержание каждого запроса находятся в разделе 6.2; там нет ничего, кроме идентификаторов установки и параметры запрашиваемой операции.
    • ❌ Фоновая активность. Нет потоков, таймеров, демонов или заданий cron. Ядро - это активен только внутри вызова метода.
    • ❌ Самообновляющийся. Ядро не загружает и не заменяет свой собственный двоичный файл.
    • ❌ Отключение проверки по протоколу TLS. Проверка сертификата включена всегда; в библиотеке нет настроек, позволяющих отключить его.
    • ❌ Разрушительные действия без вашего ведома. Единственная разрушительная операция на ваши данные — db_restore (воссоздание базы данных из резервной копии) — выполняются только на явный вызов с панели управления. Принудительное применение лицензии не затрагивает данные.
    • ❌ Читаю что-нибудь лишнее. За пределами каталога конфигурации ядро выполняет только чтение /etc/machine-id, /proc/self/status, имя хоста, шесть файлов панели для проверка авторства и файлы, которые вы явно передали (дамп для восстановления).
    • ❌ Небезопасный для памяти код. Ядро написано на Rust; используется только небезопасный код на границе с PHP.

    10. Как убедиться во всем этом самостоятельно¶

    Ни для одного из приведенных ниже шагов не нужны исходные тексты или наши секреты.

    Список методов. Подтвердите, что класс содержит именно то, что указано в разделе 5 описывает, и никаких глобальных функций: 

    php --rc XC_VM          # every method of the class
php --re xcvm_core      # everything the extension registers: the class, ini directives

    Сетевые адреса и время, когда с ними связываются. Захват трафика и подтверждение ядро отправляется только по одному адресу и только при выполнении явных действий в панели: 

    sudo tcpdump -n -i any 'port 443 and not host <your DB IP>'
    При загрузке PHP, во время нормальной работы потоков и пользователей, нет запросы. Они отображаются при регистрации, установке модуля, просмотре каталога — и не чаще одного раза в день для проверки водительских прав.

    Системные вызовы. Подтвердите отсутствие сетевой активности при запуске PHP и отсутствие доступа к неожиданные файлы. Примечание: strace started from scratch отслеживает процесс с самого начала. первая инструкция, поэтому под ней находится ядро не будет загружаться (то есть anti-debugging from section 3 — class_exists("XC_VM") returns false, which also подтверждает, что проверка действительно существует). Поэтому используйте инструменты без ptrace: 

    # a fresh process, via eBPF (linux-tools / perf package):
sudo perf trace -e 'connect,openat' php -r 'var_dump(class_exists("XC_VM"));'
    Вы увидите результаты чтения файлов /proc/self/status, /etc/machine-id в конфигурации каталог — и ни одного connect().

    Чтобы посмотреть поведение во время выполнения, подключитесь к уже запущенному рабочему файлу php-fpm — проверка отладчика выполняется только при загрузке, и рабочий процесс уже прошел ее: 

    sudo strace -f -e trace=network,openat -p $(pgrep -f 'php-fpm: pool' | head -1)
    Выполняйте действия на панели и наблюдайте: подключения идут только к вашей базе данных/Redis и — при установке модуля или проверке лицензии — значение www.xcvm.tech.

    Что находится в каталоге конфигурации. Сравните с таблицей, приведенной в разделе 4: 

    sudo ls -la /home/xc_vm/config/ /home/xc_vm/config/cluster/ 2>/dev/null

    Что записано в двоичный файл. Никаких секретов или паролей в открытом доступе: 

    strings xcvm_core.so | grep -iE 'password|secret|xcvm\.tech'

    Что такое основные раздачи PHP. config_server() не возвращает пароли: 

    php -r 'var_dump(XC_VM::config_server());'

    Поведение без подключения к сети. Ограничить доступ к серверу до www.xcvm.tech — panel, streams, DB and modules keep working; license_valid() for a confirmed key остается true.

    Определение. php -r 'var_dump(XC_VM::verify_branding());' — true на нетронутая панель.

    11. Честно говоря, о границах дозволенного¶

    Мы не утверждаем, что защита является абсолютной. На этом все заканчивается:

    • Кодер PHP не является абсолютным. Пользователь Root на своем собственном лицензированном компьютере может в теория извлекает ключевую фразу из закодированного файла, открывает свой собственный .lic и получите ключ декодирования. Машинная привязка и короткий срок службы .lic делают это более дорогие и снабжены выключателем, но это является фундаментальным ограничением любое решение, похожее на ионный куб.
    • Утечка install_id сам по себе не раскрывает ни config.enc (значение также требуется machine-id), ни кластерные транспортные большие двоичные объекты (внутренний "перчик" тоже нужен).
    • Закрытый API не имеет прямой секретности против долгоживущего сервера транспортный ключ: его компрометация приведет к раскрытию ранее зарегистрированных обменов данными, и восстановление означает отправку нового ядра с новым ключом. Адрес, размеры сообщений и хронометраж виден на проводе в любом случае — оболочка скрывает корпус, а не метаданные.
    • Проверка авторства осуществляется на основе файлов и, следовательно, его можно обойти путем редактирования файлы на собственном компьютере; это скорее отпугивает, чем делает невозможным.
    • Правоприменение осуществляется на уровне грантов БД, и ГЛАВНЫЙ администратор может переиздайте их. Это сделано намеренно: ядро не должно нарушать ваш установка, даже по команде владельца платформы.

    Вот что означает прозрачность: описание не только того, что защищено, но и там, где заканчивается защита.

    12. Часто задаваемые вопросы¶

    Can the core delete or corrupt my data? Только db_restore воссоздает базу данных заново, и только тогда, когда вы сами начинаете восстановление из резервная копия. Ничто другое, включая отзыв лицензии, не затрагивает данные.

    What if the licence server shuts down or becomes unreachable? Подтвержденная лицензия продолжает работать в автономном режиме неограниченное время; панель управления, потоки, база данных и модули работают. Единственное, что останавливается, - это загрузка новых модулей и обновлений из хранилища и создаем новый .lic для модуля (существующие .lic файлы работают до истечения срока их действия).

    Does the core see my users, streams, traffic? Это открывает соединение с вашей базой данных по запросу панели, как это сделал бы код PHP, но отправляет эти данные в никуда. Содержание каждого внешнего запроса приведено в разделе 6.2.

    Can the platform owner "switch off" my panel? Нет. Самое большее, что происходит при отзыве лицензии, описано в разделе 7.4: узлы потеряйте доступ к центральной базе данных, и ГЛАВНЫЙ администратор может повторно предоставить этот доступ. ГЛАВНОЕ, что данные, потоки и пользователи остаются незатронутыми.

    Why not just open the sources? Поскольку ядро - это то место, где хранятся пароли базы данных и ключи платных модулей; это является причиной существующим является то, что они не могут быть прочитаны из PHP. Вместо источников мы предоставляем полное описание поведения (на этой странице) и способы его проверки с помощью снаружи (раздел 10).

    Can I run the core under a debugger or profiler? Если процесс PHP равен начатый в рамках инструмента ptrace (gdb, strace php ...), ядро не загружается в этом процессе — это проверяется один раз при запуске. Присоединение к уже запущенному процессу возможно (strace -p, gdb -p): отсутствует повторите проверку, и это будет сделано намеренно — цель защиты состоит в том, чтобы остановить модуль ключи считываются из памяти с помощью отладчика во время их получения, а не для чтобы вы не наблюдали за своим собственным сервером. Инструменты без ptrace (perf, eBPF, tcpdump) на них это никак не влияет.

    Резюме. xcvm_core выполняет именно то, что нужно панели: сохраняет конфигурацию и обеспечивает доступ к базе данных/Redis без паролей в PHP, предоставляет и защищает модули, проверяет лицензию и обслуживает кластер. Он связывается с одним сервером, только когда панель вызывает его и отправляет только идентификаторы установки и рабочие параметры. Он не содержит бэкдора, не собирает телеметрию, не затрагивает ваши данные и не может быть отключенным извне. Каждое из этих утверждений на этой странице сопровождается способ убедиться в этом самому.
