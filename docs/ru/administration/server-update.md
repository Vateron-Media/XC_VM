# Обновление сервера

Пошаговое руководство по обновлению сервера XC_VM. Более подробную информацию о процессе обновления смотрите в разделе [Механизм обновления](../administration/update-system.md).

> 💾 MAIN сбрасывает свою базу данных в `/home/xc_vm/backups/pre_update_<from>_to_<to>_<timestamp>.sql` перед выполнением миграции обновления, когда на диске есть место для этого. По-прежнему рекомендуется создать собственную [резервную копию](../administration/backup-strategy.md) перед обновлением.

## Обновление через панель управления

**Шаг 1.** Откройте раздел **Серверы** в верхнем меню панели.

![Servers menu](../../_media/update1.png)

**Шаг 2.** Выберите **Управление серверами** в выпадающем меню.

![Manage Servers item](../../_media/update2.png)

**Шаг 3.** Найдите целевой сервер в таблице серверы и нажмите кнопку меню в столбце **Действия**.

![Actions button](../../_media/update3.png)

**Шаг 4.** Выберите **Серверные инструменты** в меню.

![Server Tools item](../../_media/update4.png)

**Шаг 5.** В диалоговом окне **Серверные инструменты** нажмите кнопку **Сервер обновлений**.

![Update Server button](../../_media/update5.png)

При нажатии на кнопку в базу данных заносится сигнал `update`. В течение минуты CRON распознает его, и обновление выполняется автоматически: панель останавливается, обновляется и перезапускается. Вы можете отслеживать прогресс с помощью версии сервера в таблице **Управление серверами**.

## Обновление каждого подсистемы балансировки нагрузки: Постоянное обновление

**Серверы → Массовое обновление → Обновление всех серверов** отправляет обновление сразу на каждый сервер, поэтому каждая загрузка
балансировщик перезапускается одновременно. **Серверы → Массовое → Постоянное обновление** обновляет их **по одному за раз.
время** вместо этого, до выхода MAIN:

1. Сначала обновите ГЛАВНОЕ меню.
2. Нажмите **Постоянное обновление** и подтвердите. Подсистемы балансировки нагрузки, которые подключены к сети, но не подключены к главному
релизы обновляются по очереди, по идентификатору сервера.
3. Каждый из них должен вернуться в сеть после выхода MAIN в течение 20 минут и оставаться в Сети в течение минуты,
перед запуском следующего обновления. Подсистема балансировки нагрузки, которая не останавливает текущее обновление: те
после этого все остается как есть, а на странице указывается, что произошло.

В карточке над таблицей серверов отображается прогресс каждого подсистемы балансировки нагрузки. **Отменить** обновление прекращается
перед запуском следующего балансировщика нагрузки; тот, который обновляется в этот момент, завершается сам по себе. Прокси-серверы запускают свои
собственный выпуск и не являются его частью. Из командной строки на главном:

```bash
sudo -u xc_vm /home/xc_vm/console.php cluster:rolling-update
```

## Обновление вручную (CLI)

```bash
sudo -u xc_vm /home/xc_vm/console.php update update
```

Загружает и применяет последнее обновление с GitHub. Обычно запускается автоматически через веб-панель.

## Каналы обновления

**Настройки → Общие → Обновления** устанавливает канал разблокировки для каждого компонента. Канал панели также применяется ко всем подсистемам балансировки нагрузки.

|Канал|Панель принимает|
|---------|----------------|
| `Stable` |Только стабильные релизы|
| `Beta` |Стабильные версии и пре-релизы|
| `Dev (nightly)` |Все, что есть в `Beta`, плюс ночные сборки ветки `main` (`X.Y.Z-dev.N`)|

Балансировщик нагрузки, все еще работающий на стабильной версии 2.3.9 или на бета-версии до версии 2.4.x, считывает одну настройку для своего канала (`update_channel`: `stable` или `unstable`). MAIN поддерживает связь с каналом панели (`unstable` для `Beta` и `Dev`), поэтому такой сервер следует за панелью в бета-версии. С 2.6.0 по 2.6.4 эта настройка отсутствовала, и такой балансировщик нагрузки оставался в своем выпуске, отвечая "Уже обновлен": сначала обновите MAIN, затем снова обновите балансировщик нагрузки.

`Dev` предлагается только для панели управления. Ночные сборки публикуются в отдельном репозитории [XC_VM_Dev](https://github.com/Vateron-Media/XC_VM_Dev/releases) не чаще одного раза в день и только при изменении `main`.

> ❗️ Ночные сборки не тестируются. Используйте `Dev` только на тестовых серверах: в ходе ночной сборки может быть применен перенос базы данных, который будет изменен в более поздней сборке.

Чтобы оставить значение `Dev`, переключите канал обратно на `Stable`. Приложение nightly `X.Y.Z-dev.N` старше версии `X.Y.Z`, поэтому панель обновляется до этой версии сразу после ее публикации. Чтобы сразу вернуться к предыдущему выпуску, используйте [откат](#rolling-back-a-server). Ночные сборки никогда не предлагаются в качестве целей для отката.

## Откат сервера назад

Если при обновлении возникает проблема, вы можете откатить сервер к более ранней версии непосредственно из панели. Откат выполняется для каждого сервера, поэтому как панель **главный**, так и отдельный **Балансировщики нагрузки** могут быть понижены независимо друг от друга.

**Шаг 1.** Откройте раздел **Серверы** → **Управление серверами**.

**Шаг 2.** Найдите целевой сервер и откройте его меню **Действия** (то же меню, что использовалось для обновления).

**Шаг 3.** Нажмите **Версия для отката**. Откроется диалоговое окно со списком более ранних версий (сначала самых новых). Предварительные сборки помечены тегом `(beta)`.

**Шаг 4.** Выберите версию, к которой требуется выполнить откат, и подтвердите ее.

Нажатие кнопки **Отмена** вводит сигнал `rollback` (содержащий выбранную версию) в базу данных. В течение минуты CRON распознает его, и откат выполняется автоматически, повторно используя тот же процесс остановки → замены → перезапуска в качестве обновления. Отслеживайте прогресс с помощью серверной версии в таблице **Управление серверами**.

> 💾 На сервере **главный** перед откатом автоматически создается резервная копия базы данных, которая сохраняется в `/home/xc_vm/backups/pre_rollback_<from>_to_<to>_<timestamp>.sql`. В системах балансировки нагрузки нет базы данных, поэтому этот шаг пропущен.

Предлагаемые версии зависят от канала обновления сервера: на канале `stable` отображаются только стабильные версии; на каналах `beta` и `dev` вы также видите предварительные версии `(beta)`.

> ➡️ Откат до версии 2.6.0 или более поздней **не отменяет перенос базы данных**; Откат до версии 2.5.3 или более ранней отменяет те, которые отправляют обратный файл. Схема разработана таким образом, чтобы поддерживать обратную совместимость, а автоматическое резервное копирование - это путь восстановления, если более старая сборка не может считывать новые данные. Используйте откат только в качестве шага восстановления.

### Ручной откат (CLI)

```bash
sudo -u xc_vm /home/xc_vm/console.php update rollback 2.4.0
```

Загружает указанный релиз с GitHub и применяет его с теми же проверками целостности и — в основном — автоматическим резервным копированием базы данных.
