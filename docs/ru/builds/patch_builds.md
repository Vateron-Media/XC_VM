# <a id="patch-builds"></a>Сборки патчей

Сборка исправлений содержит исправления для панелей без выпуска новой версии. Это версия с исправлениями, внесенными с тех пор, опубликованная как `X.Y.Z-pN` (`2.6.5-p1`, `2.6.5-p2`, ...) одним запуском рабочего процесса.

Используйте его для исправления, которое не должно ждать следующего выпуска. Ничего не подготавливается вручную: нет изменений в версии, нет записи `changelog.json`, нет пропуска на перевод, нет рекламы релиза.

## <a id="what-a-panel-sees"></a>Что видит панель

- Программа обновления панели обновляет патч так же, как и релиз: **Обновление** на главном экране, затем на каждом load balancer. В панели нет ничего нового.
- Патч — это **небольшое обновление**: в его архиве обновлений содержатся только файлы, измененные с момента выпуска, который он исправляет, и программа обновления накладывает их на дерево и перезапускает службу, а не повторно загружает всю панель. Панель отображает обновление в верхней строке и на странице настроек с помощью кнопки **Сервер обновлений**, нажимаемой одним нажатием, так же, как и для выпуска. В delta предполагается, что версия, в которую он вносит исправления, уже установлена, поэтому панели **ниже** для этой версии никогда не предлагается исправление: сначала предлагается полный базовый релиз (полный архив, который можно безопасно применять из любой версии), а при следующей проверке, как только он будет включен, исправление будет загружено основание.
- Он доступен на канале выпуска, содержащем исправления. Патч стабильного выпуска доступен на каналах `Stable` и `Beta`; патч предварительного выпуска доступен только на `Beta`.
- Версии упорядочены следующим образом `2.6.5` < `2.6.5-p1` < `2.6.5-p2` < `2.6.6`. Панель, посвященная выпуску, сразу переходит к его последнему исправлению, а затем к следующему выпуску, когда он появится. Панель из более старой версии переходит сразу к самой новой версии **полный**; ей не отправляется патч, на базе которого она еще не установлена (это наложило бы дельту не на то дерево) — сначала она попадает в базу, а затем в патч.
- На панели отображается версия патча (`2.6.5-p1`). Модуль, запрашивающий core `2.6.5`, продолжает загружаться: исправление считается его выпуском.
- При откате может быть указана сборка исправления или релиз под ним.
- Список изменений, отображаемый на панели, содержит все исправления с момента выпуска, поэтому в нем перечислено все, что было добавлено в обновление.

## <a id="making-one"></a>Создание одного из них

1. Объедините исправление (с `main` или с ветвью, вырезанной из выпуска, когда `main` содержит работу, которая должна подождать).
2. Запустите **Действия → Сборка исправления → Запуск рабочего процесса**, или:

    ```bash
    gh workflow run build-patch.yml -f ref=main
    ```

3. Рабочий процесс выбирает версию (`base`: самый новый тег `X.Y.Z`, который содержит ссылка), нумерует патч, запускает модульные тесты, добавляет версию в сборку и публикует `XC_VM.zip`, `xc_vm.tar.gz`, `loadbalancer.tar.gz`, `hashes.md5` и `changelog.json`. Только `xc_vm.tar.gz` (ОСНОВНОЙ архив обновлений) сокращено до **дельта** по сравнению с `base` (обновлениями release it) — файлы, которые изменились с момента выпуска, плюс файл с прошитой версией, записи каталога, чтобы оверлей сохранял древовидные режимы, и список удаленных файлов, когда что-то было убрано. `XC_VM.zip` остается полный ОСНОВНОЙ установщик, потому что при новой установке создается все дерево. `loadbalancer.tar.gz` также остается **полный**: это как полезная нагрузка обновления LB, так и его единственный установщик — `server:install` извлекает собственный релиз MAIN (который после исправления равен `X.Y.Z-pN`), чтобы подготовить новый узел, и нет эквивалента LB для `XC_VM.zip`, поэтому разница там можно было бы поместить частичное дерево на чистый узел.

|Ввод|Значение|
|-------|---------|
| `ref` |Разветвляйте, помечайте или фиксируйте для сборки. По умолчанию `main`.|
| `base` |Выпуск для исправления (`X.Y.Z`). Пусто: самый новый выпуск, который содержится в ссылке.|
| `dry_run` |Только тестирование и сборка. Ничего не публикуется; файлы хранятся как артефакт запуска в течение 7 дней.|

Если вы сомневаетесь, сначала попробуйте использовать `dry_run`.

## <a id="what-it-refuses"></a>От чего он отказывается

- Ссылка, которая не содержит релиз или является самим релизом (нечего отправлять).
- Ссылка, исходным кодом которой уже является следующая версия (`XC_VM_VERSION` отличается от базовой): это следующий релиз, поэтому выпустите его. Чтобы исправить более старый релиз, создайте его из ветки, которая все еще содержит его версию.
- Вторая сборка коммита, который уже является новейшим патчем.

## <a id="what-a-patch-may-carry"></a>Что может нести в себе пластырь

A patch build is built from the full tree of its ref: everything merged since `base` goes out, database migrations included. The MAIN update archive (`xc_vm.tar.gz`) is then a delta of those changes against `base` (the updater overlays it), so a file that did not change since the release is left as the panel has it; `loadbalancer.tar.gz` ships whole. Keep `main` releasable, or patch from a release branch.

Сборка патча в этом смысле не является выпуском:

- `changelog.json` в дереве исходных текстов не изменено; список изменений патча создается на основе тем для фиксации. Напишите строку темы для людей, которые будут читать ее на панели.
- Сайт документации не перестраивается для установки исправления.
- Патч более старой версии никогда не помечается как "Последний" на GitHub.

Следующий выпуск готовится как обычно ([Контрольный список перед выпуском](updates_checklist.md)). Его значение `deleted_files.txt` по-прежнему генерируется на основе последней стабильной версии, а не на основе тега исправления.
