# <a id="patch-builds"></a>Сборки патчей

Сборка исправлений содержит исправления для панелей без выпуска новой версии. Это версия с исправлениями, внесенными с тех пор, опубликованная как `X.Y.Z-pN` (`2.6.5-p1`, `2.6.5-p2`, ...) одним запуском рабочего процесса.

Используйте его для исправления, которое не должно ждать следующего выпуска. Ничего не подготавливается вручную: нет изменений в версии, нет записи `changelog.json`, нет пропуска на перевод, нет рекламы релиза.

## <a id="what-a-panel-sees"></a>Что видит панель

- Программа обновления панели обновляет патч так же, как и релиз: **Обновление** на главном экране, затем на каждом load balancer. В панели нет ничего нового.
- Он доступен на канале выпуска, содержащем исправления. Патч стабильного выпуска доступен на каналах `Stable` и `Beta`; патч предварительного выпуска доступен только на `Beta`.
- Версии упорядочены следующим образом `2.6.5` < `2.6.5-p1` < `2.6.5-p2` < `2.6.6`. Панель в релизе сразу переходит к самому последнему патчу, а затем к следующему релизу, когда он появится. Панель в более старом релизе сразу переходит к самой новой версии.
- На панели отображается версия патча (`2.6.5-p1`). Модуль, запрашивающий core `2.6.5`, продолжает загружаться: исправление считается его выпуском.
- При откате может быть указана сборка исправления или релиз под ним.
- Список изменений, отображаемый на панели, содержит все фиксации с момента выпуска, поэтому он считывается одинаково, независимо от того, из какого патча была выпущена панель.

## <a id="making-one"></a>Создание одного из них

1. Объедините исправление (с `main` или с ветвью, вырезанной из выпуска, когда `main` содержит работу, которая должна подождать).
2. Запустите **Действия → Сборка исправления → Запуск рабочего процесса**, или:

    ```bash
    gh workflow run build-patch.yml -f ref=main
    ```

3. Рабочий процесс выбирает релиз (`base`: самый новый тег `X.Y.Z`, который содержит ссылка), нумерует патч, запускает модульные тесты, добавляет версию в сборку, создает те же четыре файла, что и в релизе ( (`XC_VM.zip`, `xc_vm.tar.gz`, `loadbalancer.tar.gz`, `hashes.md5`), плюс `changelog.json` и публикует их.

|Ввод|Значение|
|-------|---------|
| `ref` |Разветвляйте, помечайте или фиксируйте для сборки. По умолчанию `main`.|
| `base` |Выпуск для исправления (`X.Y.Z`). Пусто: самый новый выпуск, который содержится в ссылке.|
| `dry_run` |Только тестирование и сборка. Ничего не публикуется; файлы хранятся как артефакт запуска в течение 7 дней.|

Если вы сомневаетесь, сначала попробуйте использовать `dry_run`.

## <a id="what-it-refuses"></a>От чего он отказывается

- Ссылка, которая не содержит релиз или является самим релизом (нечего отправлять).
- Ссылка, исходным кодом которой уже является следующая версия (`XC_VM_VERSION` отличается от базовой): это следующий релиз, поэтому выпустите его. Чтобы исправить более старый релиз, создайте его из ветки, которая все еще содержит его версию.
- Вторая сборка коммита, который уже является новейшим патчем.

## <a id="what-a-patch-may-carry"></a>Что может нести в себе пластырь

Сборка патча - это полная сборка его ссылки: все объединено с момента выхода релиза, включая перенос базы данных. Сохраняйте `main` доступным для выпуска или исправляйте из ветки релиза.

Сборка патча в этом смысле не является выпуском:

- `changelog.json` в дереве исходных текстов не изменено; список изменений патча создается на основе тем для фиксации. Напишите строку темы для людей, которые будут читать ее на панели.
- Сайт документации не перестраивается для установки исправления.
- Патч более старой версии никогда не помечается как "Последний" на GitHub.

Следующий выпуск готовится как обычно ([Контрольный список перед выпуском](updates_checklist.md)). Его значение `deleted_files.txt` по-прежнему генерируется на основе последней стабильной версии, а не на основе тега исправления.
