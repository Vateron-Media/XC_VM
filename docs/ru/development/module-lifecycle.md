# Жизненный цикл модуля

Как XC_VM обнаруживает, загружает, включает/отключает, устанавливает и распространяет модули во время выполнения. Чтобы создать модуль, смотрите [Создание модуля](module-authoring.md); для его расширений смотрите [Точки расширения модуля](module-extension-points.md).

## Включение / выключение модулей


Все обнаруженные модули загружаются по умолчанию. Используйте `src/config/modules.php` для переопределения состояния:

```php
return [
    'my-module' => ['state' => 'disabled'],  // preferred
    // or legacy boolean (still accepted):
    'my-module' => ['enabled' => false],
];
```

Доступные значения `state` (подкрепленные перечислением `ModuleState`):

|Ценность|Значение|
| ----- | ------- |
| `enabled` |Загрузка модуля (по умолчанию)|
| `disabled` |Модуль обнаружен, но пропущен|
| `installing` |Переходное состояние, заданное значением `ModuleManager` во время установки|
| `failed` |Ошибка установки; модуль пропущен (не загружен)|

> **Панельная диагностика.** На странице **Модули** отображается желтый значок ** Вопрос ⚠ ** рядом со статусом модуля, когда модуль считывает `Enabled`, но не загружен: требуемая зависимость отсутствует или не включена (например, `plex` считывает `Enabled`, а `watch` - `failed`), его `requires_core` исключает это ядро, или его `module.json` не может быть загружено. Во всплывающей подсказке к значку перечислены конкретные проблемы, например, `Not loaded: it has a module.json that cannot be loaded (…).` Это поле `dependency_warnings` вычисляется с помощью `ModuleManager::listModules()`.
>
> Для страницы, списка ее модулей и каждой операции с модулями (действия со строками, загрузка ZIP-файла, установка из хранилища) требуется разрешение `settings`.

Чтобы переопределить класс, разрешенный для модуля:

```php
return [
    'my-module' => ['class' => 'XcVm\\Module\\MyModuleV2\\MyModuleV2Module'],
];
```

`config/modules.php` содержит только переопределения. Пустой или отсутствующий файл означает, что все обнаруженные
загружаются модули.

`ModuleManager` сохраняет свою собственную запись в той же записи. `installed_version` - это версия
из файлов модуля на диске. `schema_version` отображается рядом с ним только в том случае, если схема
перед этими файлами: после сохранения **Отмена** или после обновления или загрузки, которые
произошел сбой после того, как были применены некоторые из его настроек. Это версия, с которой будет выполнено следующее обновление.
выбирает свои значения дельты, поэтому примененная дельта больше не применяется. Она исчезает, когда
файлы сохраняются и при удалении. Не редактируйте их вручную.

## Как работает загрузка


`ModuleLoader` выполняет эти действия при каждом запросе:

1. Сканирование `src/Modules/*/module.json`
   - Модуль, значение которого `module.json` не может быть использовано, пропускается строкой `error_log`, и
остальное все еще загружается: файл не является объектом JSON, `dependencies` или
`optional_dependencies` - это не список имен, или `environment` - это не `main`, `lb`
или `any`. Модули, для которых это требуется, будут пропущены (шаг 4).
2. Применяет переопределения из `config/modules.php`
3. Фильтры по окружающей среде (`main` / `lb` / `any`)
4. Определяет порядок загрузки:
   - `pruneUnsatisfiableModules()` удаляет модули, требуемые зависимости которых недоступны (каскадно, с зарегистрированным предупреждением), чтобы загрузка никогда не прерывалась
   - Топологическая сортировка (DFS) по графу зависимостей
   - В пределах одной и той же группы зависимостей выполните сортировку по убыванию `priority`, затем по алфавиту
   - Выдает `ModuleCycleException` для циклов (подкласс `\RuntimeException`; циклические зависимости остаются фатальными).
`ModuleManager` поэтому отказывается устанавливать (загружать, сохранять, устанавливать, обновлять) модуль
это замкнуло бы цикл с модулями на диске; необязательные зависимости и отключенные
количество модулей
   - Отсутствующие необязательные зависимости автоматически пропускаются
5. Resolves class name: `my-module` → FQN `XcVm\Module\MyModule\MyModuleModule`
(kebab-case → PascalCase; может быть переопределен с помощью клавиши `class` в конфигурации)
6. Регистрирует автозагрузчик модуля PSR-4 (сопоставляет `XcVm\Module\<Name>` с каталогом модуля)
7. Создает экземпляр класса module
   - Модуль, файл класса которого не обрабатывается или который запускается конструктором, пропускается как один
     with an unusable `module.json`: an `error_log` line gives the reason with its file and
строка, модули, которые этого требуют, пропускаются вместе с ней, а остальные все равно загружаются.
Установка или обновление такого модуля по-прежнему завершается сбоем с указанием причины

В веб-контексте:

- `bootAll($container, $router)` → вызовы `boot()`, `registerRoutes()`, `registerNavbar()`,
и подписывается на события для каждого загруженного модуля

В контексте командной строки:

- `registerAllCommands($registry)` → вызывает `registerCommands()` для каждого загруженного модуля
- `console.php module:migrate <action> <name>` освобождает `<name>` от нагрузки, а вместе с ней
модули, которым это требуется: этот процесс выполняет шаги по установке или обновлению модуля
перед загрузкой модуля

## Marketplace: установка с помощью основного расширения


Модули с платформы устанавливаются через `ModuleManager::downloadFromPlatform()`:

```php
$manager->downloadFromPlatform(slug: 'my-module', version: '1.2.0', apiKey: $key);
```

Под капотом:

1. `XC_VM::module_install($slug, $version, $apiKey)` — основное расширение загружает, расшифровывает и распаковывает файлы
2. `installModule($slug)` — применяет схему, затем запускает `install()` в модуле. Сначала
при установке применяется значение `database.sql` (без значения, каждое значение зависит от версии модуля).
Поверх существующей установки (обновления или **Отмена**) это
сначала применяет дельты `migrations/<semver>.sql` и шаги `getMigrations()` в
   (schema version, served version], then `database.sql` when the module ships one, then
   `install()`
3. `EventDispatcher::dispatch(new PackageInstalledEvent(...))` — отправляет событие
4. `hotReload($slug, $path)` — загружает модуль в текущем запросе **без перезапуска PHP-FPM**

Когда запрос уже загрузил класс модуля (обновляется включенный модуль),
шаг 2 выполняется в отдельном процессе `console.php module:migrate` — смотрите
[Версионные миграции](module-extension-points.md#versioned-migrations-migratableinterface).

Если какой-либо шаг не выполняется, предыдущие файлы и записанная версия восстанавливаются. Версии
примененные значения дельт остаются в записи как `schema_version`, поэтому следующая попытка возобновляется после
их.

Архив, загруженный на страницу **Модули** поверх установленного модуля, устанавливается таким же образом
путь. В случае отказа в загрузке или сбоя в установке установленная копия остается в
разместить: его файлы, состояние включения/выключения и отображаемую версию.

### Перенос резервной копии: таблицы модулей

Панель сама по себе не устанавливает ни одного модуля и не ведет списка того, какому модулю принадлежит та или иная таблица. То
перенос (страница настройки → `console.php migrate`) выполняет перенос основных таблиц восстановленного XUI.one /
Xtream кодирует резервную копию, затем обрабатывает все остальные таблицы из нее (`MigrateCommand::moduleTables()`: не в
`bin/install/database.sql`, не перенесенные ядром, а не остатки старых панелей, например, их активность
журналы):

- он сохраняет таблицу в `Modules/migration/<table>.sql` (ее определение и строки) и удаляет ее из
`xc_vm_migrate`;
- он передает его установленным модулям (`LegacyTableMigrationEvent`); модуль, который принимает его, копирует
строки и файл будут удалены;
- таблица, которую никто не использовал, ожидает в своем файле: когда ее модуль установлен, файл загружается в
промежуточная таблица `legacy_<table>`, модуль копирует строки, и файл и промежуточная таблица отправляются в действие.

В конце он удаляет то, что осталось от `xc_vm_migrate` (таблицы удалены, гранты сохранены): резервная копия может иметь вес
гигабайт. Если таблицу сохранить не удалось, резервная база данных остается такой, какая она есть, и об этом сообщается в журнале.
Перед переносом на странице настройки будут перечислены таблицы, которые будут сохранены для модулей, с их
строки.

### Страница модулей

Страница (`ModulesController` отображает ее, `ModuleAjaxController` отвечает на нее) имеет две вкладки:

- **Установленный** — каждый модуль со своим статусом (`enabled`, `disabled`, `not_installed`,
`installing`, `failed`) и его действия.
- **Магазин** — модули официального магазина (`ModuleStore`). Каталог является общедоступным: он представлен в списке
без ключа API модулей, по одной странице за раз, по `XC_VM::extensions_list(null, $key, $options)`
(xcvm_core 2.4.0 и более поздних версий) с `page`, `per_page` (1-100, на странице запрашивается 50), `search` (до
100 символов) и `sort` (`name`, `popular`, `newest`, `price_asc`, `price_desc`). Каждый модуль
помечен как **Свободный**, **Приобретенный** или **Оплачено**. Модуль **свободный** устанавливается без ключа и
без регистрации панели в магазине. A **оплачиваемый** для этого нужен ключ: зарегистрируйтесь на
xcvm.tech, купите модуль и установите ключ API для модулей (Настройки → API, `platform_api_key`); с помощью
ключ, которым магазин помечает модули, купленные его пользователем (`owned`), отображается как **Приобретенный** и
устанавливаемый. Платный модуль, не купивший ссылки на страницу своего магазина (`<store>/extensions/<slug>`)
вместо установки; установка в любом случае завершается ошибкой с `not_entitled`, о чем задание сообщает как
"Этот модуль платный: купите его на xcvm.tech и установите ключ API для модулей". Каждый ответ кэшируется для
2 минуты на каждый ключ и запрос (**Освежить** запрашивает снова; при установке из хранилища кэш очищается).
Более старый добавочный номер отображает магазин только с ключом и отвечает на запросы всего списка: затем панель
запрашивает `XC_VM::plugins_check()` для каждого платного модуля и сам выполняет поиск, сортировку и вывод на страницы
(`popular` и `newest` поддерживают порядок в магазине).

Включение и выключение применяются одновременно. Все остальные действия (установка, обновление, удаление,
откат, продление лицензии, установка из хранилища, загрузка архива, проверка обновлений) - это **фоновое задание**
(`ModuleJob`): запрос помещает его в очередь и запускает `console.php module:job`, который запускает его и записывает
как это закончилось в `CACHE_TMP_PATH/module_job.json`. За раз выполняется только одно задание. Опрос на странице
`api?action=module_status` (модули и задание) до тех пор, пока задание не завершится, и выводит только то, что
ответы.

|Действие (`api?action=`)|Метод|Делает|
|------------------------|--------|------|
| `module_status` |получить|Состояние каждого модуля и текущее задание|
|`module` (`sub`, `name`)|пост|`enable`/`disable` сразу; любые другие `sub` ставят задание в очередь|
|`module_upload` (`module_zip`)|пост|Устанавливает загруженный архив в качестве задания|
|`module_store` (`page`, `per_page`, `search`, `sort`, `refresh=1`)|получить|Одна страница с модулями магазина, с `page`, `per_page`, `total`, `last_page`|

`config/modules.php` считывается с помощью `require`, который OPcache кэширует в каждом из четырех PHP-FPM
мастера. При каждом чтении сначала удаляется кэшированная копия, если файл изменился на диске
(`ModuleManager::revalidate()`), таким образом, изменение, внесенное одним мастером, - это то, что обслуживают и загружают другие.

## Изолированные подсистемы


Модуль может быть полностью изолированной подсистемой со своей собственной точкой входа и начальной загрузкой
(например, Ministra). Это **соглашение**, а не маркерный интерфейс — он остается
обычный модуль `ModuleInterface`/`BaseModule`:

```php
class MyModule extends BaseModule {

    public function getName(): string {
        return 'my-module';
    }

    public function getVersion(): string {
        return '1.0.0';
    }
}
```

Изоляция означает, что подсистема работает через свою собственную общедоступную точку входа (например,
`my-module/portal.php`, путь относительно `src/`, который обрабатывает свой собственный bootstrap)
с отдельным путем начальной загрузки. Он использует общую инфраструктуру (базу данных, кэш, конфигурацию), но
участвует ли **нет** в основных `Router`, `ModuleLoader::bootAll()` или
`NavbarRegistry`. Реализации `boot()` и `registerRoutes()` обычно являются
оставлено как унаследованное бездействие.

## Обнаружение пакета Composer


Модули могут распространяться в виде пакетов Composer с `"type": "xcvm-module"`:

```json
{
    "name": "vendor/my-xcvm-module",
    "type": "xcvm-module",
    "extra": {
        "xcvm": {
            "module-path": "src"
        }
    }
}
```

`ModuleLoader` автоматически сканирует `vendor/composer/installed.json` (Composer 1 и 2
форматирует) и обнаруживает все установленные пакеты `xcvm-module` вместе со встроенным
каталог `src/Modules/`. Пакеты дедуплицируются — модуль как в `modules/`, так и в
`vendor/` загружается только один раз.
