# <a id="cli-tools-console-reference"></a>Инструменты CLI и ссылка на консоль

Справочник по интерфейсу командной строки XC_VM, системным инструментам и процессу обновления базы данных после обновления версии. Описывает ежедневные операции, аварийный доступ и создание новых этапов обновления базы данных.

---

## <a id="console-entry-point"></a>Точка входа в консоль

Все команды CLI выполняются через `console.php`:

```bash
/home/xc_vm/console.php <command> [args...]
```

Консоль поддерживает три типа команд:

|Тип|Рассчитывать|Описание|
| --- | --- | --- |
| **Commands** |28|Одноразовые операции (обновление, статус, инструменты и т.д.)|
| **CronJobs** |25|Запланированные задачи (автоматически вызываемые crontab)|
| **Daemons** |8|Длительно выполняющиеся фоновые процессы (команды, использующие `DaemonTrait`)|

> **Примечание:** Демоны - это обычные команды, которые используют `DaemonTrait`. Отдельного каталога `Daemons/` не существует.

Чтобы просмотреть все доступные команды:

```bash
/home/xc_vm/console.php list
```

## <a id="binary-self-update-self-heal"></a>Бинарное самообновление (самовосстановление)

Некоторые связанные двоичные файлы **нет** поставляются внутри пакета heavy runtime bundle и будут
в противном случае никогда не обновляйтесь между выпусками панели (новый узел LB или узел, оставленный включенным
старая сборка, никогда не сходилась бы). `cron:root_signals` (root, каждую минуту) сохраняет
они становятся текущими путем опроса их идемпотентных команд обновления для каждого двоичного файла на
расписание с ограниченным использованием штампов - каждая загрузка выполняется только при несоответствии версии, проверяется
контрольная сумма, запуск-тестирует новый двоичный файл, затем заменяет его атомарно (неработающая загрузка
никогда не заменяет рабочий). Выполняется на каждом узле (main **и** LB).

|Двоичный|Команда|Источник|Проверить|Опрос|
| --- | --- | --- | --- | --- |
|`xc_fanout` демон и `xc_agent`| `fanout_binary` |`XC_VM_Fanout` высвобождение активов|`SHA256SUMS` (+ испытание агента в `run.sh`)|~ежечасно|
|`xcvm_core` расширение| `xcvm_core` |`XC_VM_Binaries` дерево репозиториев (`bin/xcvm_core/`)|`SHA256SUMS` + нагрузочный тест|~ежечасно|
| `yt-dlp` | `ytdlp` |вышестоящий `yt-dlp/yt-dlp` релиз|`SHA2-256SUMS` + `--version`|ежедневный|
|`ffmpeg`/`ffprobe` 4.4, 7.1, 8.1|`ffmpeg` (как xc_vm)|`XC_VM_FFMPEG` релиз, сборки этого дистрибутива|`hashes.md5` + оба двоичных файла должны быть запущены|ежедневный|

Марки живут в `CRONS_TMP_PATH` (`fanout_binary_check`, `xcvm_core_check`,
`ytdlp_check`, `ffmpeg_check`); первый проход (штамп отсутствует) выполняется немедленно, поэтому новый
install/LB получает двоичный файл в течение минуты. Каждый узел запускает их, независимо от его
групповой режим: ОСНОВНОЙ игрок не раздает ничего из этого. `fanout_binary` принимает `fanout` или
`agent` для обновления одного из двух параметров; при выключенном разветвлении проверка выполняется ежечасно.
`fanout_binary agent`. Выпуск агента, который был откатан `run.sh` на узле, не является
извлекается оттуда снова, пока не появится более новая (`xc_agent.tried`; `force` повторяет попытку
это).

С установленным параметром release canary (Настройки → Кластер, *Release Canary*: идентификатор сервера подсистемы балансировки нагрузки; 0,
значение по умолчанию выключено), только этот подсистема балансировки нагрузки принимает каждый из двух выпусков, как только он выходит.
Каждый другой сервер, включая MAIN, принимает новейшую версию на уровне или ниже пин-кода, который MAIN повышает один раз
the canary запустила выпуск для *Release Canary Hours*, который активен и его слышно повсюду. Сервер
тот, у кого уже запущен более новый релиз, сохраняет его, и до тех пор, пока не будет введен первый пин-код, остальные не получат ничего. Пин-код
изменения внесены в кластерный аудит (`release.pin`).

`ffmpeg` выводит `ffmpeg_<label>_<distro>.tar.gz` для каждой метки на страницу настроек
предложения (в архивах релизов отсутствует файл ffmpeg: установщик и установка LB
запустите и его), встроенного в контейнер этого дистрибутива, чтобы его glibc соответствовал интерфейсу узла.,
и заменяет каждое из них на `bin/ffmpeg_bin/<label>/` только после того, как оно начнется здесь.
`ffmpeg_bin/ffmpeg_version.json` записывает релиз каждого лейбла; запуск, который сделал
не завершено (уничтожено, GitHub недоступен), повторная попытка выполняется через час.

Каждая папка в `bin/ffmpeg_bin/` представляет собой одну сборку, и в ней хранятся настройки версии FFmpeg
его название:

|Папка|Что это такое|
|---|---|
|`<major>.<minor>` (`4.4`, `7.1`, `8.1`)|Сборка XC_VM. Название - это настоящая младшая версия сборки. Обновления патчей (7.1.5 → 7.1.6) заменяют ее на прежнюю, поэтому настройки никогда не меняются.|
|`<major>.<minor>-<vendor>` (`6.1-my`)|Чужая сборка. Команда `ffmpeg` никогда не записывает и не заменяет ее. Поместите пользовательскую сборку в папку с таким именем.|

Папка `4.0` - это сборка XUI на панели, перенесенной из XUI (или более старой XC_VM
build); он также никогда не меняется.

Панель запрашивает у каждого двоичного файла, что это такое, вместо того, чтобы доверять его папке или
`BUILD_INFO`: на странице настроек отображается версия двоичных отчетов, `ffmpeg`
устанавливает сборку только в том случае, если ее двоичный файл сообщает версию метки, и
`-nofix_dts` (Переключатель XUI для устаревшего пути DTS, также в сборке XC_VM версии 4.4)
переходит только к сборке, в которой `ffmpeg -h full` перечислены `-fix_dts`; запас ffmpeg будет
откажитесь от этого. Ответы сохраняются в кэше до тех пор, пока не изменится двоичный файл. Параметр
присвоение имени сборке, в которой отсутствует узел (скажем, более старое `4.0` или `8.0`), требует того же второстепенного значения.
сначала версия, затем самая новая из основных, затем самая новая сборка, так что никаких
настройки необходимо переписать. Папки с именем `*.backup.*` игнорируются и никогда не удаляются.

Вместо этого тяжелый пакет runtime (nginx, nginx_rtmp и PHP) обновляется с помощью
команда `binaries`, запускаемая сигналом `update_binaries` от MAIN. Пакет является
устанавливается только в том случае, если в `hashes.md5` его версии указан MD5 архива и
загрузка соответствует ему; в противном случае запущенные двоичные файлы сохраняются, и причина находится в
`tmp/binaries_update_*.log`.

## <a id="registering-a-new-command"></a>Регистрация новой команды

Все команды CLI реализуют `CommandInterface`. Основные команды автоматически обнаруживаются из `src/Cli/` с помощью отражения в `console.php`. Команды модуля регистрируются с помощью `ModuleLoader::registerAllCommands()`.

### <a id="commandinterface"></a>Командный интерфейс

```php
interface CommandInterface {
    public function getName(): string;        // Unique command name (used in CLI)
    public function getDescription(): string; // One-line help text (shown in `list`)
    public function execute(array $rArgs): int; // Entry point, returns exit code
}
```

### <a id="step-1-create-the-class"></a>Шаг 1. Создайте класс

Создайте новый файл в `src/Cli/Commands/` (или `src/Cli/CronJobs/` для заданий cron):

```php
<?php

class MyNewCommand implements CommandInterface {

    public function getName(): string {
        return 'my_command';
    }

    public function getDescription(): string {
        return 'Short description of what it does';
    }

    public function execute(array $rArgs): int {
        // Your logic here
        echo "Done.\n";
        return 0; // 0 = success, 1 = error
    }
}
```

Для команд **демон** также используйте `DaemonTrait`:

```php
class MyDaemonCommand implements CommandInterface {
    use DaemonTrait;
    // ...
}
```

Для **задания cron** используйте `CronTrait`:

```php
class MyCronJob implements CommandInterface {
    use CronTrait;

    public function getName(): string {
        return 'cron:my_job'; // Cron names are prefixed with cron:
    }
    // ...
}
```

### <a id="step-2-registration-is-automatic"></a>Шаг 2. Регистрация происходит автоматически

Есть **нечего добавить к `console.php`**. При запуске он выдает `Cli/Commands/*.php` и
`Cli/CronJobs/*.php` и, посредством отражения, `register()` для каждого неабстрактного класса, реализующего
`CommandInterface`. Переместите ваш класс в нужный каталог (с помощью `getName()`, который возвращает
его имя команды) — это все, что требуется - смотрите [Подключение ядра → регистрация команды CLI](../development/core-wiring.md#cli-command-registration).

### <a id="step-3-add-to-makefile-if-lb-excluded"></a>Шаг 3. Добавить в Makefile (если LB-исключен)

Если команда не должна включаться в сборки подсистемы балансировки нагрузки, добавьте ее путь к `LB_FILES_TO_REMOVE` в поле `Makefile`.

### <a id="step-4-test"></a>Шаг 4. Тестирование

```bash
# Verify it appears in the list
/home/xc_vm/console.php list

# Run it
/home/xc_vm/console.php my_command
```

## <a id="tools-command"></a>Команда инструментов

Команда `tools` предоставляет утилиты для обслуживания системы.

```bash
/home/xc_vm/console.php  tools <subcommand>
```

### <a id="subcommands-run-as-root"></a>Подкоманды (запускаются как `root`)

|Подкомандование|Описание|
| --- | --- |
| `rescue` | Create a temporary rescue access code for emergency panel access. Prints the URL. **Delete this code after use!** |
| `recaptcha` |Отключите reCAPTCHA (`recaptcha_enable = 0`), чтобы восстановить вход в панель администратора при сбое проверки captcha.|
| `access` |Восстановите все настройки кода доступа к nginx и перезагрузите nginx. Печатает URL-адреса для всех кодов панели администратора.|
| `ports` |Восстановите настройки портов nginx (HTTP, HTTPS, RTMP) из базы данных и перезагрузите nginx.|
| `migration` |Очистите промежуточную базу данных (`xc_vm_migrate`) и при необходимости восстановите в ней резервную копию `.sql`.|
| `user` |Создайте пользователя rescue admin со случайными учетными данными. Введите имя пользователя и пароль. **Удалите этого пользователя после использования!**|
| `mysql` |Повторно авторизуйте привилегии MySQL для всех серверов балансировки нагрузки.|
| `database` |Восстановите пустую базу данных XC_VM из `database.sql`. **Стирает ВСЕ данные!** Требуется флаг `--confirm`.|
| `flush` |Очистить все заблокированные IP—адреса - удаляет собственные правила блокировки панели (`-s <address> -j DROP` в `INPUT`, IPv4 и IPv6) за одну фиксацию для каждого семейства адресов, удаляет файлы блокировки и обрезает таблицу `blocked_ips`. Все остальные правила, цепочки и политики брандмауэра остаются в покое.|
| `twofactor <username>` |Отключите двухфакторный вход пользователя для администратора или торгового посредника, которые потеряли свое приложение для проверки подлинности и коды восстановления. Если это требуется группе пользователей, при следующем входе в систему это будет сделано заново.|

### <a id="subcommands-run-as-xc_vm"></a>Подкоманды (запускаются как `xc_vm`)

|Подкомандование|Описание|
| --- | --- |
| `images` |Загрузите отсутствующие изображения потоковых передач/фильмов/сериалов из базы данных TMDB. Сканирует базу данных в поисках URL-адресов изображений и загружает отсутствующие файлы.|
| `duplicates` |Найдите и удалите повторяющиеся VOD-трансляции. Группируйте по идентичным источникам, сначала сохраняйте, а остальные удаляйте. **Разрушительный!**|
| `bouquets` |Удаляет устаревшие ссылки из букетов. Удаляет идентификаторы, которые больше не существуют в базе данных. Программа может выполняться во время добавления элементов в импорт. Одновременно выполняется только одно сканирование, а одно ожидает; запуск, начатый во время ожидания, сразу возвращается и завершает работу.|

### <a id="examples"></a>Примеры

```bash
# Emergency panel access (root)
sudo /home/xc_vm/console.php tools rescue

# Disable reCAPTCHA to recover admin login (root)
sudo /home/xc_vm/console.php tools recaptcha

# Regenerate access codes (root) — required after nginx template changes
sudo /home/xc_vm/console.php tools access

# Regenerate port configuration (root)
sudo /home/xc_vm/console.php tools ports

# Clear staging database (root)
sudo /home/xc_vm/console.php tools migration

# Clear staging database and restore a backup (root)
sudo /home/xc_vm/console.php tools migration /path/to/backup.sql

# Create rescue admin user (root)
sudo /home/xc_vm/console.php tools user

# Turn off two-factor sign-in for a locked-out admin (root)
sudo /home/xc_vm/console.php tools twofactor admin

# Reauthorise MySQL privileges on all servers (root)
sudo /home/xc_vm/console.php tools mysql

# Restore blank database (root) — DESTRUCTIVE!
sudo /home/xc_vm/console.php tools database --confirm

# Flush all blocked IPs (root)
sudo /home/xc_vm/console.php tools flush

# Download missing images (xc_vm)
su - xc_vm -c '/home/xc_vm/console.php tools images'

# Remove duplicate VOD entries (xc_vm)
su - xc_vm -c '/home/xc_vm/console.php tools duplicates'

# Clean orphaned bouquet references (xc_vm)
su - xc_vm -c '/home/xc_vm/console.php tools bouquets'
```

- ⚠️ **Предупреждение:** `duplicates` стримы и все связанные с ними данные (журналы, статистика, эпизоды, записи) удаляются безвозвратно. Всегда создавайте резервную копию перед запуском.
- ⚠️ **Предупреждение:** `database --confirm` удаляет всю базу данных и заменяет ее пустой схемой. Это необратимо.
- 💡 **Совет:** После запуска `rescue` всегда удаляйте код через панель администратора или запустив `tools access`, как только вы восстановите доступ.
- 💡 **Совет:** После запуска `user` немедленно измените пароль и по завершении удалите пользователя для восстановления.

## <a id="common-cli-operations"></a>Общие операции CLI

### <a id="status-check"></a>Проверка состояния

```bash
sudo /home/xc_vm/console.php status
```

Проверяет, запущен ли XC_VM, подключается к базе данных, выполняет ожидающие обновления шаги, исправляет разрешения и проверяет конфигурацию nginx. Требуется после установки или восстановления.

С аргументом `first-run` пропускает текущую проверку, используемую для начальной настройки:

```bash
sudo /home/xc_vm/console.php status first-run
```

`status` и `startup` проверяют crontab root и выводят одну из трех строк. `Crontab already installed` - это обычная строка при каждом запуске. `Crontab installed` отображается только при изменении списка записей. `Crontab not installed: ...` означает, что новый список не удалось создать, и старый crontab был сохранен.

### <a id="service-management"></a>Управление услугами

```bash
sudo /home/xc_vm/console.php service start|stop|restart|reload
```

### <a id="manual-update"></a>Обновление вручную

```bash
sudo -u xc_vm /home/xc_vm/console.php update update
```

Загружает и применяет последнее обновление с GitHub. Обычно запускается автоматически через веб-панель.

### <a id="stream-diagnostics"></a>Диагностика потока

```bash
sudo -u xc_vm /home/xc_vm/console.php monitor <stream_id>
```

Запускает поток вручную и отображает все ошибки. Полезно для диагностики сбоев при запуске потока.

### <a id="server-node-diagnostics"></a>Диагностика сервера (узла)

```bash
# On the MAIN — remote-probe a node by its server id
sudo /home/xc_vm/console.php server:diagnose <server_id>

# On the LB/proxy node itself — local self-diagnosis (no arguments)
sudo /home/xc_vm/console.php server:diagnose
```

Обнаруживает **почему?** прокси—сервер/LB—узел, отображаемый в автономном режиме на панели: проверяет частоту сердечных сокращений, доступность (ICMP/TCP/HTTP `/api`), перекос часов, очередь сигналов, поддерживает ли LB основной `OPENSSL_EXTRA` и - локально на узле - поддерживает ли узел установил брандмауэр на IP-адрес главного сервера в его собственных iptables, независимо от того, запущена ли служба `xc_vm`/nginx, запущен ли демон `watchdog` heartbeat и находится ли `cron:servers` в crontab `xc_vm`. Доступно только для чтения; код выхода `0` = проблем не обнаружено, `2` = указаны вероятные причины. Более подробную информацию смотрите в [Руководстве по диагностике сервера](../administration/server-diagnostics.md).

### <a id="openssl_extra-sync"></a>Синхронизация OPENSSL_EXTRA

```bash
# On the MAIN — one load balancer, or every LB that reports another value
sudo /home/xc_vm/console.php server:sync-openssl-extra <server_id>
sudo /home/xc_vm/console.php server:sync-openssl-extra --all [--force]
```

Переводит балансировщики нагрузки на основное значение `OPENSSL_EXTRA`, когда `server:diagnose` сообщает о несоответствии (воспроизведение, перенаправленное с основного, завершается сбоем на этом LB). Каждое LB применяет это значение в течение минуты и сохраняет прежнее значение в течение 10 минут. Смотрите [Устранение несоответствия OPENSSL_EXTRA](../administration/server-diagnostics.md#repairing-an-openssl_extra-mismatch).

### <a id="ssl-certificate"></a>SSL-сертификат

```bash
sudo /home/xc_vm/console.php certbot
```
