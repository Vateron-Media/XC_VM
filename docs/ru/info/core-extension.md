# <a id="core-extension-xcvm_core-what-it-does-stores-sends-and-what-it-doesnt"></a>Основное расширение (xcvm_core): Что оно делает, хранит, отправляет — и чего не делает

Эта страница предназначена для XC_VM пользователей и администраторов. Основная часть (`xcvm_core.so`)
поставляется в виде скомпилированного двоичного файла без исходного кода, и это является законной причиной для
задавать вопросы. Итак, на этой странице описано **все его поведение**: что происходит при
время загрузки, какие файлы он создает, каждое действие, которое он может выполнить, каждая сеть
запрос и что именно содержит каждый из них, как работает лицензирование и что именно
происходит, когда лицензия отзывается, а также что делает ядро **нет** и как это сделать
**проверяйте каждое утверждение самостоятельно** со стандартными инструментами Linux, без исходных текстов.

Страница является самодостаточной: она не отсылает вас больше никуда.

---

## <a id="1-in-short-what-it-is"></a>1. Вкратце: что это такое

`xcvm_core` - это собственное расширение PHP (написанное на Rust), которое загружается в PHP
процессы панели XC_VM и регистры класса **один**, `XC_VM` со статическим
методы. Он не добавляет никаких глобальных функций и не устанавливает никаких перехватчиков в код PHP
исполнение.

Это решает ровно три проблемы:

|Проблема|Что он делает|
|---------|--------------|
| **Config, DB, Redis** |Сохраняет настройки панели в зашифрованном виде, используя машинные `config.enc` и ручные PHP готовые MySQL/Redis соединения, чтобы пароли никогда не появлялись в коде PHP.|
| **Modules** |Загружает модуль из хранилища в виде одного архива в запечатанном конверте, распаковывает его и выполняет атомарную замену. Все `*.php` в нем уже закодированы в ionCube; стандартный загрузчик ionCube выполняет это. Ключа модуля нет, и расшифровывать нечего|
| **Licence and cluster** |Проверяет лицензию на установку и позволяет главному серверу передавать конфигурации и токены узлов LB без передачи паролей|

Это **нет**: черный ход, канал дистанционного управления, средство сбора телеметрии, способ
для эксфильтрации ваших данных или механизма выполнения кода, отправленного извне. То
ниже приводится подробная информация по каждому из этих утверждений.

## <a id="2-why-the-core-is-a-binary"></a>2. Почему ядро является двоичным

Код панели PHP открыт и может быть прочитан любым пользователем, имеющим доступ к серверу. Если
пароли к базам данных, закрытые ключи или логика лицензирования хранились в нем, они отправлялись
первому, кто открыл файл. Таким образом, именно эти данные будут перенесены в
скомпилированный код:

1. **Пароли к базе данных и Redis** никогда не появляются в PHP: ядро считывает их из
`config.enc` сам по себе и сам открывает соединение.
2. **Ключевой материал** никогда не отображается в PHP: закрытый ключ панели, кластер MAIN
root и материал токена cluster API остаются запечатанными на компьютере и доступны
используется только внутри ядра. (Модулям вообще не нужен ключ: их код защищен
лицензия ionCube, а не что-либо из того, что содержится в ядре.)
3. **Проверка лицензий** нельзя закомментировать, отредактировав PHP.

В этом весь смысл закрытого двоичного файла. Его поведение не является секретом —
это описано здесь.

## <a id="3-what-happens-when-php-loads"></a>3. Что происходит при загрузке PHP

В начале каждого процесса PHP (php-fpm, CLI) ядро инициализируется. Это
полный список того, что произойдет потом — и ничего больше:

1. **Проверка с помощью отладчика.** Файл `/proc/self/status` прочитан. Если процесс завершен
отслеживается прямо сейчас (`TracerPid` ненулевое значение - например, подключен gdb),
ядро **отказывается загружаться**. Больше ничего не происходит: ничего не удаляется, ничего
отправляется куда угодно, сервер не останавливается — класс `XC_VM` просто
недоступен в этом процессе.
2. **Нет директивы `php.ini`.** Ядро не регистрирует none и не считывает none; каждая настройка
встроен в двоичный файл (см. раздел 8.4).
3. **Проверка наличия загрузчика ionCube.** Если он не загружен, выдается обычное PHP предупреждение
передается. Это всего лишь сообщение — ядро продолжает работать.
4. **Идентификатор установки.** Если файл `keys/install_id` еще не существует,
генерируется случайный UUID и записывается в каталог конфигурации с `0600`
разрешения. Если он существует, он считывается. Вычисляется отпечаток среды
в то же время (ничего не отправляется).
5. **Автоматическая миграция конфигурации.** Если в конфигурации есть старый открытый текст `config.ini`
каталог, а `config.enc` - нет, ini считывается, шифруется в `config.enc`,
и `config.ini` тогда равно **удаленный** (таким образом, пароли в виде открытого текста не сохраняются
диск). Если `config.enc` уже существует, ничего не происходит. Если не существует ни того, ни другого,
ничего не происходит.

**Ядро не выполняет никаких сетевых запросов во время загрузки.** Каждый запрос к
сервер работает только внутри вызовов методов, перечисленных в разделе 5.

Ядро не создает фоновых потоков, таймеров, демонов или заданий cron. Все, что в нем есть
это происходит внутри вызова метода, созданного панелью, и заканчивается этим вызовом.

## <a id="4-what-the-core-keeps-on-your-disk"></a>4. Что ядро хранит на вашем диске

Все секретные данные для каждой установки хранятся в **каталог конфигурации** — по умолчанию
`/home/xc_vm/config` (разрешения `0700`). Путь может быть переопределен с помощью
`XCVM_CONFIG_DIR` переменная окружения — переменная окружения **только**, которая
ядро считывает данные.

Ядро хранит свои ключи в `keys/`, а файлы лицензий - в `licence/`, оба `0700`
([ADR-006](https://github.com/Vateron-Media/XC_VM_CoreExtention/blob/main/docs/adr/ADR-006-config-dir-layout.md)).
Ядро, существовавшее до этого макета, хранило их непосредственно в каталоге конфигурации;
первое ядро с его помощью перемещает каждый файл на место один раз, при загрузке, и оставляет символическую ссылку
под старым именем (`install_id -> keys/install_id`), так что старое ядро все еще находит
оно. Спросите ядро, существует ли идентификатор с `identity_present()`, а не с
ищу файл.

|Файл|Что это такое|Режим|
|------|-----------|------|
| `config.enc` |Настройки панели (база данных, Redis, роль сервера), шифрование AES-256-GCM. Ключ получен из `install_id` **и** `/etc/machine-id`, таким образом, копия на другом компьютере не расшифровывается| `0600` |
| `keys/install_id` |Случайный UUID вашей установки. Создается один раз и никогда не изменяется (несмотря на обновления ядра и PHP)| `0600` |
|`keys/panel.pk` / `keys/panel.sk`| The panel's X25519 key pair. The public half is sent to the server at registration (and is what MAIN seals a load balancer's config to); **the private half never leaves the machine** and is stored sealed to this machine's key |ск: `0600`|
| `licence/activation_key` |Лицензионный ключ активации (вы вставляете его в панель). Подписан сервером, привязан к вашему `install_id`| `0600` |
| `licence/license_verdict` |Кэш последнего подписанного ответа сервера о состоянии лицензии| `0600` |
| `licence/license_checkin` |Временная метка, указывающая, когда может состояться следующая ежедневная регистрация заезда (см. раздел 7).|—|
|`licence/license_enforce_ts` / `licence/license_revoked`|Временные метки последнего применения отозванной лицензии и сама отметка об отзыве (см. раздел 7.4)|—|
| `cluster/` |Файлы кластера: корневые ключи MAIN (`root.enc`), закрепленные ключи MAIN на LB (`core.pin`), состояние отзыва узла (`nodes.state`), защищенные часы (`clock.sealed`, `timeanchor`), аренда LB (`lease`), основные показатели из конфигураций, установленных LB (`xcvt.hwm`, см. раздел 5.6). Все зашифровано с помощью ключа этой машины| `0600` |

За пределами каталога конфигурации ядро записывает:

- to `/home/xc_vm/Modules/<module>/` — файлы установленных модулей (путь указан следующим образом
исправлено);
- временный файл в `/tmp` с разрешениями `0600` — параметры подключения для
`mysqldump`/`mysql` во время дампа/восстановления базы данных; файл ** удаляется сразу после
операция**.

Что записывает ядро **нет**: что-либо за пределами этих путей, скрытые файлы или
изменяется на `php.ini`, cron, systemd или автозапуск.

## <a id="5-the-complete-list-of-the-cores-actions"></a>5. Полный список действий ядра

Ниже приведены **все** методов класса `XC_VM`. Для каждого из них: что он делает, что он
касается диска, базы данных и сети. Знак "—" в столбце "Сеть" означает, что
метод не выполняет сетевых запросов. Ни один метод не запускается сам по себе — только когда панель
называет это.

### <a id="51-installation-identity"></a>5.1. Идентификация установки

|Метод|Что он делает|Диск|Сеть|
|--------|-------------|------|---------|
| `install_id()` |Возвращает установочный UUID (создает его при первом вызове)|считывает/создает `keys/install_id`|—|
| `identity_present()` |Независимо от того, существуют ли `keys/install_id` и `keys/panel.sk`, **не создавая ни того, ни другого**: что запрашивает панель перед `install_id()` или `panel_pk()`, где отсутствующий идентификатор должен оставаться отсутствующим|не воспринимает ничего, кроме их присутствия|—|
| `env_fingerprint()` |Возвращает хэш `SHA-256(install_id + /etc/machine-id + hostname)`. Это **хэш**: имя хоста или идентификатор компьютера не могут быть восстановлены из него|считывает `/etc/machine-id`, имя хоста|—|

### <a id="52-panel-config"></a>5.2. Настройка панели управления

|Метод|Что он делает|Диск|Сеть|
|--------|-------------|------|---------|
| `config_init(data)` |Записывает `config.enc` во время установки панели (база данных, Redis, роль сервера). Затем удаляет старый открытый текст `config.ini`|записывает `config.enc`|—|
| `config_set_redis(host, port, auth)` |Обновляет **только** раздел Redis раздела `config.enc` (требуется при изменении пароля Redis)|записывает `config.enc`|—|
| `config_server()` |Возвращает раздел `server` (идентификатор сервера, независимо от того, является ли он LB). Возвращает ли **нет** пароли|считывает `config.enc`|—|
| `config_set_db(pass)` |На узле LB от имени root: заменяет пароль базы данных на `config.enc` и ничего больше (половина смены пароля узла). Отказывает в ГЛАВНОМ|записывает `config.enc`|—|

Каждая запись `config.enc` является атомарной: записывается временный файл, который затем переименовывается
поверх старого. В случае сбоя в любой момент остается либо старый файл, либо новый,
никогда не бывает пустым или испорченным.

### <a id="53-database-and-redis"></a>5.3. База данных и Redis

Все методы считывают учетные данные из `config.enc` внутри ядра; ** они никогда не
достичь PHP**.

|Метод|Что он делает|Диск|Сеть|
|--------|-------------|------|---------|
| `db_connect()` |Возвращает готовое PDO-соединение с вашей базой данных|считывает `config.enc`|только ваша база данных|
| `redis_connect()` |Возвращает готовое соединение Redis|считывает `config.enc`|только для вашего Redis|
| `db_dump(file, ignore_tables)` |Выгружает базу данных через `mysqldump` (структура, затем данные) в данный файл|записывает данный файл; временный `.cnf` в `/tmp`, после чего удаляется|только ваша база данных|
| `db_restore(file, dbname)` |**Отбрасывает и воссоздает заново** в целевую базу данных, затем импортирует файл. Операция уничтожения, но она выполняется **только по явному вызову** с панели (восстановление из резервной копии)|временный `.cnf` в `/tmp`, впоследствии удаленный|только ваша база данных|
| `db_grant(host)` |Предоставляет привилегии пользователя панели управления базой данных при подключении с указанного адреса (для узла LB).|—|только ваша база данных|
| `db_revoke(host)` |Отменяет привилегии для данного адреса. **Отказывается** для отмены адресов MAIN сам может подключаться через (`localhost`, loopback, хост базы данных из конфигурации) — таким образом, MAIN никогда не будет отключен от своей собственной базы данных|—|только ваша база данных|
| `db_set_password(new)` |На ГЛАВНОЙ: изменяет пароль пользователя панели в базе данных, затем в `config.enc`, затем в разрешениях узлов. Если запись конфигурации завершается неудачно, пароль базы данных отменяется|записывает `config.enc`|только ваша база данных|

Адрес в `db_grant`/`db_revoke` строго проверен (допустимы только символы
в хосте MySQL), и значения заключаются в кавычки с помощью PDO — SQL-инъекции через эти
методы невозможны.

### <a id="54-modules-store-installation-module-licence"></a>5.4. Модули: хранение, установка, лицензия на модуль

|Метод|Что он делает|Диск|Сеть|
|--------|-------------|------|---------|
| `panel_register(api_key)` |Регистрирует панель на сервере: создает (или считывает) пару ключей панели и отправляет `install_id`, **общественный**, `env_fp` и `hw_id`|создает `panel.pk`/`panel.sk`| `panel/register` |
| `plugins_check(plugin, install_id, api_key)` |Запрашивает у сервера, доступен ли модуль для установки|—| `plugins/check` |
| `plugins_token(plugin, install_id, api_key)` |Получает с сервера кратковременный (5-минутный) токен доступа к модулю|—| `plugins/token` |
| `extensions_list(env, api_key, options)` |Возвращает каталог магазина (постраничный, с поиском и сортировкой)|—| `extensions` |
| `extensions_check_update(list, api_key)` |Запрашивает, существуют ли обновления для списка установленных модулей|—| `extensions/check-update` |
| `module_install(slug, version, api_key)` |Полный цикл установки модуля (см. ниже)|записывает `Modules/<slug>/`|`plugins/token`, `plugins/download`|
| `module_license(slug, server_data, api_key)` |Запрашивает файл лицензии ionCube `.lic` для модуля, подключенного к вашему компьютеру|— (панель записывает файл)|`plugins/token`, `plugins/license`|

**Как устанавливается модуль (`module_install`)**, шаг за шагом:

1. С сервера запрашивается токен доступа к модулю. Сервер проверяет, является ли
владелец ключа API имеет право на доступ к этому модулю. Для модуля **свободный**
не требуется ни API-ключ, ни регистрация в панели управления. Пустая версия означает "the
последний одобренный вариант".
2. Архив модуля (`tar.gz`) загружен. Ответ сервера приходит внутри
запечатанный конверт (см. раздел 6.1), и архив ** используется только в том случае, если
конверт открывается** — т.е. доказано, что он пришел с сервера и отвечает на это
очень прошу. Любой сбой на этом шаге = установка невозможна, ничего не записывается в
диск.
3. Архив извлекается в промежуточный каталог, расположенный рядом с каталогом модуля.
(`/home/xc_vm/Modules/.<slug>.new.<random>/`). Архив, содержащий символический
ссылка или любой файл в зашифрованном формате, который был удален для каждого файла (`*.xcvm`), отклоняются.
4. Промежуточный каталог заменяется на `/home/xc_vm/Modules/<slug>/` атомарно
(`renameat2` с `RENAME_EXCHANGE`; обычный `rename` при первой установке), и
предыдущее дерево удалено. Каталог модуля заменен целиком: файлы в новом
версия, которая больше не поставляется, удалена. Установка осуществляется последовательно с помощью блокировки модулей
каталог.

Сбой на любом этапе приводит к удалению промежуточного каталога и сохранению предыдущей версии
нетронутый. Нет ключа модуля и нет расшифровки: модуль - это те же файлы, что и на
каждая машина, и то, что заставляет ее работать только там, где она была лицензирована, - это ionCube
лицензия (ниже).

After that the core **has nothing to do with the module**: the files on disk are
обычные файлы в кодировке ionCube `.php`, выполняемые стандартным загрузчиком ionCube через
PHP обычный механизм. Ядро ничего не расшифровывает за запрос, не перехватывает PHP
компиляция и не выполняет никакого кода.

What is in a module archive: `module.json` (the manifest — the panel reads it), the
файлы модуля `*.php` (все в кодировке ionCube) и все остальные файлы разработчика
отправил его.

**Лицензия на модуль (`module_license`).** Необязательный шаг для платных модулей. Панель
передает ядру машинный отпечаток пальца, созданный самой ionCube
(`ioncube_server_data()`); ядро отправляет его на сервер; сервер отчеканивает
`.lic` Файл, привязанный к этому компьютеру, имеет ограниченный срок службы. Файл находится рядом с
модуль; без совпадения `.lic` загрузчик ionCube не расшифровывает код модуля.
файлы — эта лицензия обеспечивает защиту модуля от копирования. Если лицензирование модуля
отключено на сервере или права доступа отсутствуют, панель просто пишет "нет".
`.lic`.

### <a id="55-installation-licence-and-attribution"></a>5.5. Лицензия на установку и указание авторства

`verify_branding()` никогда не подключается к сети; `license_valid()` делает это только для
обновите устаревший вердикт (раздел 7). `license_check()` специально запрашивает сервер.

|Метод|Что он делает|Диск|Сеть|
|--------|-------------|------|---------|

**Конфигурация load balancer: XCVT v1 и v2.** Большой двоичный объект `config_pack` создается следующим образом
файл `XCVT`. Версия 2 (был предоставлен ключ) подписана MAIN и запечатана в
узел; версия 1 (без ключа) сохраняется для узлов, которые еще не закреплены и доступны для чтения
и поддается подделке любым, у кого есть `.so` и `install_id` узла, так что это делает
не защищает закрепленный узел. Заголовок версии 2 имеет размер 110 байт, за которым следует запечатанный текст:

|Поле|Байты|Содержание|
|-------|-------|---------|
|магия|4| `XCVT` |
|версия|1| `0x02` |
|добрый|1|`1` конфигурация, `2` вывод|
| `created_ms` |8|время создания, миллисекунды в Unix, порядок строк в нижнем конце|
| `main_sign_pub` |32|Ключ подписи Ed25519 от MAIN|
|подпись|64|Подпись MAIN в течение первых 14 байт и текст|
|тело|остальное|привязан к узлу `panel_pk()`, привязан к заголовку и узлу `install_id`|

То, что принимает узел, соответствует его состоянию pin-кода:

|Узел|Принимает|Отказывается|
|------|---------|---------|
|не закреплен|в1|v2 (`NOT_PINNED`)|
|закрепленный|v2, подписанный ОСНОВНЫМ, к которому он прикреплен|v1 (`CRYPTO`)|

Кроме того, `install_config` принимает большой двоичный объект только в том случае, если он адресован этому узлу,
имеет возраст не более часа, это конфигурация (не pin-код), предназначена для load balancer (`is_lb` 1)
и, когда конфигурация уже создана, она предназначена для этого узла `server_id`. Конфигурация версии 2
более старый, чем последний, установленный с того же подписчика (или такой же старый с другим
тело) отклоняется как `RECORD:replay`; последнее принятое время сохраняется в запечатанном
файл `cluster/xcvt.hwm`, который содержит `cluster_pin` с `replace` и импорт из
ключи кластера очищаются. При отказе ничего не записывается; его причина доступна через
`cluster_last_error()`. Как администратор закрепляет load balancer:
[Подписанные, запечатанные конфигурации load balancer](../administration/main-lb-cluster.md#signed-sealed-load-balancer-configs-xcvt-v2).

Что гарантирует ядро в кластере независимо от того, что делает PHP: закрытые ключи
и материал токена никогда не покидает ядро; отзыв узла сохраняется после восстановления базы данных;
перевод часов назад (на основной или на LB) ничего не меняет; узел, переключенный на
в режиме API без использования учетных данных учетные данные не возвращаются без явного указания
действие администратора.

## <a id="6-network-every-request-and-what-it-carries"></a>6. Сеть: каждый запрос и то, что он несет

Ядро взаимодействует с **только один внешний адрес** — хранилищем и сервером лицензий
`https://www.xcvm.tech` (каждый путь из `/api/v1/`). Он больше нигде не соединяется,
кроме **твой** DB и **твой** Redis по адресам из вашей собственной конфигурации.

### <a id="61-how-every-request-is-built"></a>6.1. Как строится каждый запрос

Каждый запрос к серверу представляет собой `POST`, тело которого равно **запечатанный** для сервера.
открытый ключ поверх TLS (конверт "XCVM-API-v1"). Внутри конверта находится
временная метка, одноразовый идентификатор запроса, ключ API (при необходимости) и само тело запроса.
Ответ сервера привязан к одноразовому ключу, известному только вашей панели, например
это единственная просьба.

Почему: чтобы тела запроса и ответа не могли быть прочитаны или заменены даже
где TLS завершается на промежуточном этапе (прокси-сервер, load balancer,
nginx→переход php-fpm на стороне сервера). Эта защита работает **в вашу пользу**:
ваш API-ключ не передается в HTTP-заголовке и невидим на промежуточном сервере
переходы, и загруженный модуль не может быть заменен при передаче.

Параметры клиента:

- Только HTTPS; включена проверка цепочки сертификатов и имени хоста, и ** не может быть
отключено в любом месте** — в используемой библиотеке просто нет такой настройки;
- в перенаправлении отказано (301/302 = ошибка);
- нет прокси-сервера: `HTTPS_PROXY` и его родственники в среде PHP игнорируются, каждый
запрос отправляется непосредственно на сервер;
- тайм-ауты: обычный запрос - 15 секунд, загрузка архива - 120 секунд, подключение - 10 секунд;
- размер архива не более 100 МБ;
- ни на клиенте, ни на сервере нет режима открытого текста (незапечатанного).

### <a id="62-the-complete-request-table"></a>6.2. Полная таблица запросов

|Конечная точка|Когда|Что отправляется|
|----------|------|-------------|
| `panel/register` |регистрация панели в магазине|`install_id`; ключ панели **общественный**; `env_fp` (хэш); `hw_id` (хэш из `install_id + machine-id`); API-ключ|

| `plugins/download` |установка модуля|пуля, версия, токен|
| `plugins/license` |запрашивает `.lic` для модуля|токен; отпечаток пальца машины ionCube (`ioncube_server_data()`)|

### <a id="63-what-is-never-in-a-request"></a>6.3. Чего никогда нет в запросе

- ❌ данные о ваших пользователях, подписчиках, плейлистах, потоках, EPG;
- ❌ содержимое вашей базы данных или Redis;
- ❌ пароли — база данных, Redis или система;
- ❌ закрытые ключи, `config.enc`;
- ❌ имя хоста или `/etc/machine-id` в открытом виде — только их хэш;
- ❌ статистика использования, журналы, списки IP-адресов ваших клиентов, данные о загрузке;
- ❌ все, что находится "в фоновом режиме": каждый запрос в таблице выполняется внутри
вызов метода с помощью панели, и ни один из них не выполняется во время загрузки PHP или по основному таймеру.

Единственный "регулярный" контакт — проверка прав, не чаще одного раза в день — также происходит
**внутри** вызов `license_valid()`, сделанный панелью, а не самим ядром
инициатива; что она несет в себе, указано в таблице выше.

## <a id="7-licensing-how-it-works-and-what-happens-on-revocation"></a>7. Лицензирование: как это работает и что происходит при отзыве лицензии

Да, ядро проверяет лицензию. В этом разделе подробно описано, как и что происходит
без доступа к сети и что происходит при отзыве. Ничего из этого не скрыто.

### <a id="71-the-activation-key"></a>7.1. Ключ активации

Лицензия на установку представляет собой текстовый ключ формы `XCVM1.<data>.<signature>`, который
администратор вставляет данные в панель; они сохраняются в файле `activation_key`.
Ключ имеет значение **подписанный сервером** (Ed25519) и содержит:

- `hwid` — ваш `install_id`: ключ работает только при той установке, при которой он был выдан
для;
- `jti` — идентификатор ключа;
- `iat` — время выдачи;
- `exp` — срок действия (может отсутствовать = бессрочный).

Подпись, привязка и срок действия проверяются **не в сети** без подключения к сети.

### <a id="72-the-attribution-requirement"></a>7.2. Требование об атрибуции

Панель XC_VM распространяется под лицензией AGPL-3.0, и условия использования
в лицензионных функциях сохраняется авторская принадлежность. Ядро проверяет это: оно
считывает шесть собственных файлов панели (`Core/Util/AdminHelpers.php` и пять
нижний колонтитул/шаблоны входа в систему на панелях администратора, реселлера и игрока) и следит за тем, чтобы
строки атрибуции на месте (`github.com/Vateron-Media/XC_VM`,
`Vateron Media`, ссылка на AGPL-3.0) и что вызов рендеринга нижнего колонтитула не является
закомментировано.

- The check is **purely file-based**: no network, no cryptography.
- Если количество файлов равно **отсутствовать** (нестандартная компоновка, разработка), то проверка
считается равным **пройденный**: ядро не блокирует установку из-за отсутствующих файлов.
- Если атрибуция была удалена, `license_valid()` возвращает `false`, т.е.
**лицензированный** функции (разветвление, чеканка кластерных токенов) отключены. Панель
сами по себе ваши потоки, база данных и пользователи продолжают работать.
- Вердикт кэшируется в течение 1 секунды, поэтому файлы не считываются при каждом запросе.

### <a id="73-the-server-check-and-behaviour-without-network"></a>7.3. Проверка и поведение сервера без подключения к сети

На ГЛАВНОЙ странице `license_valid()` = "атрибуция установлена" **и** "ключ активации действителен".
Срок действия включает в себя отзыв, и именно так ядро узнает об этом:

- Ответ сервера о состоянии ключа кэшируется в `license_verdict`
файл. Кэш подписан сервером и не может быть подделан.
- Когда кэш устарел (или отсутствует), ядро внутри `license_valid()` вызывает —
отправляет запрос `activation/status`; ответ проверяется подписью, с помощью
однократно `nonce` и по `jti`, и только затем сохраняются в кэше.
- На ОСНОВНОМ, дополнительно, один раз в день (20 часов плюс случайный сдвиг на 8 часов,
чтобы избежать скачков нагрузки) вводится значение `activation/checkin` — те же данные. Узлы LB
не проводите регистрацию заезда.

**Behaviour without server access — the key point:**

- Ключ, который сервер подтвердил хотя бы один раз **, остается действительным в автономном режиме
бессрочно**. Недоступный сервер лицензий**никогда** не превращает оплаченный
установка в неоплачиваемый режим.
- Ключ, который сервер никогда не подтверждал (например, просто вставил, пока нет
сеть) работает в течение **14 дней** с момента его выпуска.
- A licence is considered invalid in exactly two cases: the `exp` recorded in the
сам ключ был передан, **или** сервер отправил ответ **подписанный** "ключ отозван".
Сетевая ошибка, тайм-аут или неразборчивый ответ - это **нет** аннулирование.

### <a id="74-what-exactly-happens-on-revocation-enforcement"></a>7.4. Что именно происходит при отзыве (приведении в исполнение)

Об этом стоит знать заранее. Если лицензия недействительна **подтвержденный** (то
два случая выше), и только на сервере **главный** ядро выполняет две функции:

1. Записывает файл маркера `license_revoked` с временной меткой в конфигурацию
каталог.
2. Отменяет в вашей базе данных права доступа пользователя панели **для LB/proxy
адреса узлов** (берется список адресов из вашей таблицы `servers`
где `is_main = 0` и выполняется `REVOKE ALL PRIVILEGES` для каждого). Каждый адрес
сначала выполняется строгая проверка символов, чтобы исключить SQL-инъекцию через таблицу.

Это выполняется максимум **раз в час**. Что он делает **нет**:

- ❌ он не удаляет и не изменяет ваши данные — ни одной строки, ни одной таблицы;
- ❌ это не затрагивает собственный доступ MAIN к своей базе данных;
- ❌ это не останавливает PHP, nginx или потоки и не удаляет модули или файлы;
- ❌ он ничего не отправляет на сервер;
- ❌ Узлы LB **никогда** обеспечивают принудительное выполнение, что бы ни случилось.

Цель: отозванная лицензия лишает установку возможности **мультисерверный**
возможности (узлы теряют доступ к центральной базе данных), но не нарушает работу ни панели, ни
данные. Доступ может быть повторно предоставлен с помощью обычного `db_grant` после истечения срока действия лицензии.
восстановленный.

## <a id="8-the-protective-mechanisms-that-usually-raise-questions"></a>8. Защитные механизмы, которые обычно вызывают вопросы

### <a id="81-anti-debugging"></a>8.1. Защита от отладки
Описано в пункте 1 раздела 3. Повторим ключевой момент: это всего лишь отказ от
загружается с помощью отладчика — без побочных эффектов. Его цель - остановить ключ
материал (закрытый ключ панели, корень кластера, расшифрованная конфигурация), являющийся
извлечен из памяти запущенного процесса.

### <a id="82-hidden-strings-in-the-binary"></a>8.2. Скрытые строки в двоичном коде
Адрес сервера, пути к API и один внутренний "локальный pepper" (константа, которая
принимает участие в получении ключей, которые запечатывают локальные файлы) хранятся в двоичном коде
XOR-кодируется, поэтому `strings xcvm_core.so` их не показывает. Цель состоит в том, чтобы остановить
ядро просто переназначается на поддельный сервер. Суть одна и та же в каждом
сборка: это запутывание, а не секрет — что привязывает закрытый файл к вашему компьютеру
равно `/etc/machine-id`. Это **скрывает константы, а не поведение** — поведение таково
полностью описано здесь. Ключевые доменные имена, такие как `xcvm_cfg_v1`, отображаются в
`strings`, и это прекрасно.

### <a id="83-machine-binding-env_fp-and-hw_id"></a>8.3. Машинная привязка: `env_fp` и `hw_id`
- `env_fp` = `SHA-256(install_id + /etc/machine-id + hostname)`. "Мягкий" переплет:
сервер замечает клонирование или миграцию из-за изменения хэша, но измененный
`env_fp` **ничего не блокирует**. Если идентификатор компьютера или имя хоста недоступны, это
заменено пустой строкой.
- `hw_id` = `SHA-256(install_id + /etc/machine-id)`. Сервер сначала закрепляет его
регистрация. Если то же самое `install_id` появится с другого компьютера, **оплачиваемый**
модули перестают выдаваться с ошибкой `panel_moved` до тех пор, пока хранилище
администратор сбрасывает привязку. Это защищает от копирования одного платного
установка на множество серверов.

Оба значения являются хэшами; по ним невозможно восстановить имя вашего хоста или идентификатор компьютера.

### <a id="84-no-way-to-change-the-server-address"></a>8.4. Невозможно изменить адрес сервера
Адрес фиксирован в двоичном коде. `php.ini` вообще не считывается, и ядро
не регистрирует директиву `xcvm_core.*` (в `php --ri xcvm_core` она отсутствует); a
`xcvm_core.server_url` строка, оставшаяся в `php.ini`, игнорируется, как и все остальные
переменная среды, за исключением `XCVM_CONFIG_DIR`. Цель состоит в том, чтобы остановить ядро
быть перенаправленным, изменив одну строку, в поддельный магазин, обслуживающий поддельные модули.
Адрес должен быть `https://`.

### <a id="85-self-wiping-keys"></a>8.5. Самоочищающиеся клавиши
Закрытые ключи, производные ключи, пароли баз данных и другие ключевые материалы хранятся в
ядро в буферах, которые обнуляются в памяти при освобождении — на каждом пути выхода,
включая ошибки.

## <a id="9-what-the-core-does-not-contain"></a>9. Чего нет в ядре

- ❌ **Черный ход или пульт дистанционного управления.** Не существует метода, который выполнял бы команды или
код, отправленный сервером. Сервер может ответить данными только на запрос, который
составлена панель: каталог, жетон, архив, лицензионный вердикт.
- ❌ **Выполнение поставляемого кода ядром.** Единственное, что приходит из
сервер, а затем выполняется, является модулями, и они выполняются на складе
Загрузчик ionCube с помощью обычного механизма PHP, после того как вы сами запустили
установка. Ядро не устанавливает никаких перехватчиков для компиляции или выполнения PHP.
- ❌ **Телеметрия, шпионаж, утечка данных.** Полное содержание каждого запроса
находятся в разделе 6.2; там нет ничего, кроме идентификаторов установки и
параметры запрашиваемой операции.
- ❌ **Фоновая активность.** Нет потоков, таймеров, демонов или заданий cron. Ядро - это
активен только внутри вызова метода.
- ❌ **Самообновляющийся.** Ядро не загружает и не заменяет свой собственный двоичный файл.
- ❌ **Отключение проверки по протоколу TLS.** Проверка сертификата включена всегда;
в библиотеке нет настроек, позволяющих отключить его.
- ❌ **Разрушительные действия без вашего ведома.** Единственная разрушительная операция на
ваши данные — `db_restore` (воссоздание базы данных из резервной копии) — выполняются только на
явный вызов с панели управления. Принудительное применение лицензии не затрагивает данные.
- ❌ **Читаю что-нибудь лишнее.** За пределами каталога конфигурации ядро выполняет только чтение
`/etc/machine-id`, `/proc/self/status`, имя хоста, шесть файлов панели для
проверка авторства и файлы, которые вы явно передали (дамп для восстановления).
- ❌ **Небезопасный для памяти код.** Ядро написано на Rust; используется только небезопасный код
на границе с PHP.

## <a id="10-how-to-verify-all-of-this-yourself"></a>10. Как убедиться во всем этом самостоятельно

Ни для одного из приведенных ниже шагов не нужны исходные тексты или наши секреты.

**Список методов.** Подтвердите, что класс содержит именно то, что указано в разделе 5
описывает, и никаких глобальных функций:
```bash
php --rc XC_VM          # every method of the class
php --re xcvm_core      # everything the extension registers: the class, and no ini directives
```

**Сетевые адреса и время, когда с ними связываются.** Захват трафика и подтверждение
ядро отправляется только по одному адресу и только при выполнении явных действий в панели:
```bash
sudo tcpdump -n -i any 'port 443 and not host <your DB IP>'
```
При загрузке PHP, во время нормальной работы потоков и пользователей, нет
запросы. Они отображаются при регистрации, установке модуля, просмотре каталога —
и не чаще одного раза в день для проверки водительских прав.

**Системные вызовы.** Подтвердите отсутствие сетевой активности при запуске PHP и отсутствие доступа к
неожиданные файлы. Примечание: `strace` started from scratch отслеживает процесс с самого начала.
первая инструкция, поэтому под ней находится ядро **не будет загружаться** (то есть
anti-debugging from section 3 — `class_exists("XC_VM")` returns `false`, which also
подтверждает, что проверка действительно существует). Поэтому используйте инструменты без `ptrace`:
```bash
# a fresh process, via eBPF (linux-tools / perf package):
sudo perf trace -e 'connect,openat' php -r 'var_dump(class_exists("XC_VM"));'
```
Вы увидите результаты чтения файлов `/proc/self/status`, `/etc/machine-id` в конфигурации
каталог — и ни одного `connect()`.

Чтобы посмотреть поведение **во время выполнения**, подключитесь к уже запущенному рабочему файлу php-fpm —
проверка отладчика выполняется только при загрузке, и рабочий процесс уже прошел ее:
```bash
sudo strace -f -e trace=network,openat -p $(pgrep -f 'php-fpm: pool' | head -1)
```
Выполняйте действия на панели и наблюдайте: подключения идут только к вашей базе данных/Redis и —
при установке модуля или проверке лицензии — значение `www.xcvm.tech`.

**Что находится в каталоге конфигурации.** Сравните с таблицей, приведенной в разделе 4:
```bash
sudo ls -la /home/xc_vm/config/ /home/xc_vm/config/cluster/ 2>/dev/null
```

**Что записано в двоичный файл.** Никаких секретов или паролей в открытом доступе:
```bash
strings xcvm_core.so | grep -iE 'password|secret|xcvm\.tech'
```

**Что такое основные раздачи PHP.** `config_server()` не возвращает пароли:
```bash
php -r 'var_dump(XC_VM::config_server());'
```

**Поведение без подключения к сети.** Ограничить доступ к серверу до `www.xcvm.tech` —
panel, streams, DB and modules keep working; `license_valid()` for a confirmed key
остается `true`.

**Определение.** `php -r 'var_dump(XC_VM::verify_branding());'` — `true` на
нетронутая панель.

## <a id="11-honestly-about-the-limits"></a>11. Честно говоря, о границах дозволенного

Мы не утверждаем, что защита является абсолютной. На этом все заканчивается:

- **Кодер PHP не является абсолютным.** Пользователь Root на своем собственном лицензированном компьютере может в
теория извлекает ключевую фразу из закодированного файла, открывает свой собственный `.lic` и
получите ключ декодирования. Машинная привязка и короткий срок службы `.lic` делают это
более дорогие и снабжены выключателем, но это является фундаментальным ограничением
любое решение, похожее на ионный куб.
- **Утечка `install_id`** сам по себе не раскрывает `config.enc` (значение
также требуется `machine-id`). Это действительно открывает большой двоичный объект XCVT **в1**: перец находится в
при каждой сборке, таким образом, `.so` плюс `install_id` узла считываются и подделываются. Версия 2
большой двоичный объект подписан MAIN и привязан к собственному ключу узла, поэтому закрепленный
load balancer принимает только версию 2.
- **Закрытый API не имеет прямой секретности** против долгоживущего сервера
транспортный ключ: его компрометация приведет к раскрытию ранее зарегистрированных обменов данными, и
восстановление означает отправку нового ядра с новым ключом. Адрес, размеры сообщений и
хронометраж виден на проводе в любом случае — оболочка скрывает корпус, а не
метаданные.
- **Проверка авторства осуществляется на основе файлов** и, следовательно, его можно обойти путем редактирования
файлы на собственном компьютере; это скорее отпугивает, чем делает невозможным.
- **Правоприменение осуществляется на уровне грантов БД**, и ГЛАВНЫЙ администратор может
переиздайте их. Это сделано намеренно: ядро не должно нарушать ваш
установка, даже по команде владельца платформы.

Вот что означает прозрачность: описание не только того, что защищено, но и
там, где заканчивается защита.

## <a id="12-frequently-asked-questions"></a>12. Часто задаваемые вопросы

**Can the core delete or corrupt my data?**
Только `db_restore` воссоздает базу данных заново, и только тогда, когда вы сами начинаете восстановление из
резервная копия. Ничто другое, включая отзыв лицензии, не затрагивает данные.

**What if the licence server shuts down or becomes unreachable?**
Подтвержденная лицензия продолжает работать в автономном режиме неограниченное время; панель управления, потоки, база данных и
модули работают. Единственное, что останавливается, - это загрузка новых модулей и обновлений
из хранилища и создаем новый `.lic` для модуля (существующие `.lic` файлы работают
до истечения срока их действия).

**Does the core see my users, streams, traffic?**
Это открывает соединение с вашей базой данных по запросу панели, как это сделал бы код PHP, но
отправляет эти данные в никуда. Содержание каждого внешнего запроса приведено в разделе 6.2.

**Can the platform owner "switch off" my panel?**
Нет. Самое большее, что происходит при отзыве лицензии, описано в разделе 7.4: узлы
потеряйте доступ к центральной базе данных, и ГЛАВНЫЙ администратор может повторно предоставить этот доступ.
ГЛАВНОЕ, что данные, потоки и пользователи остаются незатронутыми.

**Why not just open the sources?**
Поскольку ядро - это то место, где хранятся пароли базы данных, а также ключи панели управления и кластера; его
причина их существования заключается в том, что они не могут быть прочитаны из PHP. Вместо источников мы предоставляем
полное описание поведения (на этой странице) и способы его проверки с помощью
снаружи (раздел 10).

**Can I run the core under a debugger or profiler?**
Если процесс PHP равен **начатый** в рамках инструмента `ptrace` (gdb, `strace php ...`),
ядро не загружается в этом процессе — это проверяется один раз при запуске. Присоединение
к уже запущенному процессу возможно (`strace -p`, `gdb -p`): отсутствует
повторите проверку, и это будет сделано намеренно — цель защиты состоит в том, чтобы остановить ввод ключа.
материал считывается из памяти с помощью отладчика * во время его использования*, чтобы не
чтобы вы не наблюдали за своим собственным сервером. Инструменты без `ptrace` (`perf`, eBPF, `tcpdump`)
на них это никак не влияет.

---

**Резюме.** `xcvm_core` выполняет именно то, что нужно панели: сохраняет конфигурацию и
предоставляет доступ к базе данных/Redis без паролей в PHP, предоставляет модули (защита от копирования обеспечивается лицензией ionCube),
проверяет лицензию и обслуживает кластер. Он связывается с одним сервером, только когда
панель вызывает его и отправляет только идентификаторы установки и рабочие параметры.
Он не содержит бэкдора, не собирает телеметрию, не затрагивает ваши данные и не может
быть отключенным извне. Каждое из этих утверждений на этой странице сопровождается
способ убедиться в этом самому.
