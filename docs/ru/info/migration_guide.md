# <a id="xc_vm-migration-guide"></a>Руководство по миграции XC_VM

Безопасная миграция с совместимых IPTV-систем с помощью встроенных инструментов миграции XC_VM.

---

## <a id="critical-migration-notice"></a>Важное уведомление о переносе

> **Read this before starting the migration.**

Миграция XC_VM переносит **только данные**.
**All configuration is intentionally excluded from migration.**

Это включает в себя (но не ограничивается этим):

- Ключи API (например, **ТМДб**)
- Учетные данные внешней службы
- Настройки, зависящие от конкретной среды
- Конфигурация панели и системы
- Время выполнения и состояние потока

Эти значения **необходимо перенастроить вручную после миграции**.

Это **дизайнерское решение**, а не ограничение или ошибка.
Пропуск реконфигурации приведет к **прерывать выборку метаданных, обновлять заголовки потоков и связанные с ними функции**.

---

## <a id="before-you-start"></a>Прежде чем Вы начнете

> 💡 **Рекомендация:**
> Выполните перенос на **новая установка XC_VM**.
>
> ⚠️ **Важный:**
> Системные настройки и настройки панели равны **НЕ перенесен**.
> Передаются только данные базы данных, поддерживаемые процессом миграции.

Если вы решите перейти на **существующая установка**, имейте в виду:

- XC_VM будет иметь значение **удалить все таблицы** в основной базе данных, соответствующее данным из базы данных миграции.
- **Резервное копирование является обязательным.** Автоматический откат не предусмотрен.

---

## <a id="migration-steps"></a>Этапы миграции

### <a id="1-upload-backup"></a>1. Загрузить резервную копию

Загрузите существующую резервную копию базы данных на сервер XC_VM, используя **SFTP-протокол**.

Примерное местоположение:

```text
/tmp/backup.sql
```

---

### <a id="2-restore-backup-into-migration-database"></a>2. Восстановить резервную копию в базе данных миграции

Очистите базу данных миграции и восстановите резервную копию:

```bash
sudo /home/xc_vm/console.php tools migration "/tmp/backup.sql"
```

Прежде чем продолжить, убедитесь, что восстановление завершено **без ошибок**.

---

### <a id="3-start-migration"></a>3. Начать миграцию

Как только резервная копия будет восстановлена, запустите миграцию, используя один из следующих способов.

#### <a id="option-1-command-line-recommended"></a>Вариант 1 — Командная строка (рекомендуется)

```bash
/home/xc_vm/console.php migrate
```

#### <a id="option-2-web-installer"></a>Вариант 2 — Веб-установщик

- Вернитесь к **веб-установщик** (ссылка, показанная при настройке панели).
- Выберите **Миграция**
- Следуйте инструкциям на экране

Вы будете видеть обновления о ходе выполнения в режиме реального времени.
После завершения работы система будет доступна.

---

## <a id="restoring-access-after-migration"></a>Восстановление Доступа После Миграции

Если войти в систему не удается из-за отсутствия учетных данных или кода доступа, воспользуйтесь средствами восстановления.

### <a id="create-a-rescue-access-code"></a>Создайте аварийный код доступа

```bash
sudo /home/xc_vm/console.php tools access
```

### <a id="create-an-administrator-account"></a>Создайте учетную запись администратора

```bash
sudo /home/xc_vm/console.php tools user
```

> ❗️ После восстановления доступа введите **немедленно измените** код доступа и учетные данные администратора.

---

## <a id="load-balancer-preparation"></a>Подготовка балансировщика нагрузки

Балансировщики нагрузки равны **не перенесен**.

- При необходимости переустановите операционную систему
- Перенастройка сети и маршрутизации
- Повторно подключите их к основному серверу

---

## <a id="post-migration-required"></a>Постмиграционный период (обязательно)

После миграции система будет находиться в состоянии **не готов к производству** до тех пор, пока эти шаги не будут выполнены.

Пропуск их приведет к результату **ожидаемое, но нарушенное поведение**.

---

### <a id="1-reinitialize-runtime-state"></a>1. Повторная инициализация состояния среды выполнения

- Запускайте все потоки вручную
- Убедитесь, что потоки доступны и стабильны

> Состояние выполнения потока во время миграции равно **никогда не сохранявшийся**.

---

### <a id="2-reconfigure-system-settings"></a>2. Перенастроить системные параметры

Просмотрите и восстановите все настройки, зависящие от конкретной среды:

- Пути к файлам
- Лимиты и квоты
- Настройки сети и обратного прокси-сервера
- Настройка производительности

> Сделайте **нет** вывод, что значения по умолчанию соответствуют вашим предыдущим настройкам.
> Значения по умолчанию применяются намеренно.

---

### <a id="3-restore-api-keys-and-providers"></a>3. Восстановление ключей API и поставщиков

#### <a id="api-keys-are-never-migrated"></a>Ключи API Никогда Не Переносятся

Следующее **необходимо перенастроить вручную**:

- **TMDb API key**

Это **ожидаемое поведение**.

> Если выборка метаданных не работает после миграции,
> убедитесь, что ключ API был повторно добавлен и поставщик включен.
> This does **not** indicate a migration bug.

---

## <a id="common-post-migration-issues"></a>Общие проблемы после миграции

### <a id="metadata-is-not-fetching-tmdb"></a>Метаданные Не извлекаются (TMDb)

**Cause:**
Ключ API TMDb и конфигурация поставщика не были восстановлены.

**Resolution:**
Повторно добавьте ключ API TMDb и включите провайдера в настройках главного сервера.

---

## <a id="summary"></a>Резюме

- Миграционные переводы **только основные данные приложения**
- Конфигурация равна **исключено по замыслу**
- Ключи API и настройки, зависящие от среды **необходимо восстановить вручную**
- Недостающая функциональность после миграции равна **ожидается до завершения реконфигурации**
